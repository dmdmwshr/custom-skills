# 从业务需求到可复用查询

目标是取得用户需要的统计数据。来源监督系统当前按用户已知条件没有可用的数据获取接口，因此用受控页面自动化采集；自建案卷系统负责结构化保存和后续查询。不要把“下载全部文件”当作每个问题的第一步，也不因统计目标自行新增系统功能或部署。

## 需求路由

1. 先明确需求中已有的对象、时间、组织、条件和交付形式，例如“本年不合格案卷”是案卷集合，不是通知书份数；“不合格产品数量”还需产品粒度及初查/复查去重口径。使用已有输入与页面事实消解常规歧义，只在会实质改变结果且无法核实时提问。
2. 查看自建系统现有数据覆盖范围、更新时间、查询筛选与导出能力。能用已核验入库数据回答时直接查询；数据不完整先说明缺口，并在用户授权范围内补采。不能把局部采集后的系统总数当成来源全量。
3. 来源查询优先采用精确类型/字段的定向筛选，减少无关详情与下载；依据页面实际控件和关联关系只读探索，不猜接口、隐藏数据或业务规律。候选记录回到详情确认身份，再去重与下载。
4. 当前授权含下载上传则执行完整流水线；只有统计/查看授权时，只读查询已有数据和页面，不顺带写入。自行探索不授权办理案件、改变审批状态或修改生产数据库。
5. 回答统计时说明：来源、时间字段和范围、覆盖组织、统计粒度/去重键、排除规则、数据截至时间、完整性与未决项。界面总数、文书数、项目数、产品数不能混用。

## 已知方法：不合格案卷

- **用户明确业务规则（2026-09-19）：**在文件/法律文书查询中搜索“责令限期改正通知书”，对应案卷就是本次不合格案卷集合。复查后合格不因此排除。该规则用于本产品监督场景，不泛化为其他模块、所有法律情形或每件产品的结论。
- **当前已实现的程序支持：**`ANNUAL_RECTIFICATION_NOTICE` 接收精确类型、现场页码、日期字段标签与查询证据引用；两轮清单稳定、RWID 到项目编号去重沿用已有流程。通知书数量不生成初查/复查标签。
- **页面验证状态：**用户已给出查询路径依据；本维护任务尚未亲自实测该直接筛选的年度完整性。交接执行任务验证后，补记实际入口、控件含义、日期语义和证据引用，再标记 `UI_VERIFIED`。不得仅因代码测试通过就升级该状态。
- **执行步骤与正式放量：**见 [年度不合格案卷](annual-unqualified.md)。结果表先列文书记录数，再列 RWID 和合并项目数；只对已确认项目开展后续整理入库。

## 沉淀方法

每条可复用方法保留：需求名称、用户定义、页面入口和筛选组合、日期字段含义、结果与案卷/产品的关系、去重键、最小验证案例、覆盖限制、验证时间和状态。状态分 `USER_DEFINED`（用户给定）、`UI_VERIFIED`（页面验证）、`INFERRED_PENDING`（推断待验证）。相似术语或一次相关性不自动升级为业务规律。

真实截图、账号、业务清单和运行回执留工作根；Skill 只记录脱敏规则和引用方式。执行任务先把新发现写工作根轻量记录，维护任务按 CC Switch 流程审查并发布规则；不让多个任务同时修改受管源。下一次相同需求直接复用已验证方法并做轻量页面漂移检查。

自建系统的业务统计入口、接口可用性与统计定义要逐项核实；现有上传/核验接口不能推定具备通用统计接口。尚未实现的查询功能记为后续能力需求，不冒称当前 Skill 已交付。
