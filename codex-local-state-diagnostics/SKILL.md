# Codex 本地状态诊断

## 定位与分工

本 skill 只处理 Codex 桌面端、原生 CLI 及其本机运行链的证据分层。默认只读，不因诊断请求而重启、退出、结束进程、安装、更新、重试、归档、改配置或改内部状态。

先读 [Linux/WSL 与 Windows 运行环境](references/platform-runtime.md)，区分执行主机、目标进程和状态目录。先检查症状对应层，不要求一次扫描全部七层。版本号、工具未暴露和 API 实测失败分别记录，不能互相替代。

- openai-docs 负责当前官方产品能力、支持范围、模型和配置文档；本 skill 不用本机异常推断官方事实。
- Windows 计划任务由目标机已安装的 `windows-task-scheduler` 处理；Linux 服务按项目 systemd 或实际启动方式处理，Codex 自动化用产品工具。本 skill 只按需核对触发与进程证据，不自动迁移调度器。
- codex-project-task-handoff 负责项目内唯一交接文档、同项目后继任务及旧任务改名归档；本 skill 只诊断其读写结果，不创建第二份交接文档或后继任务。
- cc-connect-collaboration 负责固定会话、移动通道、绑定代次和路由换代；固定会话问题不得被本 skill 当作普通项目接力处理。

浏览器不可控、启动到错误配置、页面等待误判、采集器加载差异或已登录站点复用问题，直接读取 [浏览器控制恢复](references/browser-control-recovery.md)，从相关层开始，不先扫描会话数据库、历史或网络。用户只要求诊断时保持只读；已明确要求修复目标浏览器或采集器时，必要的范围内修复、备份、测试和回读一起完成，不逐步重复确认。外部发送、凭据及项目固定会话契约继续单独约束。

## 安全边界

1. 先记录精确目标、主机、时区和症状时间窗。短 ID 前缀、显示标题、侧栏位置和目录末级名称都不能唯一识别任务。
2. 只读取完成判断所需的元数据、计数、状态、错误类别和小范围证据。不读取或输出密码、令牌、Cookie、账号、订阅链接、代理凭据、会话正文、访问正文、完整命令行或完整私有配置。
3. 先核对目标进程活动 `CODEX_HOME`：本机 WSL 为 `/root/.codex`，Windows 通常为 `%USERPROFILE%\.codex`。二者独立，不创建替代活动目录，不手工编辑 `session_index.jsonl`、`state_*.sqlite`、rollout JSONL、认证、索引或会话文件。
4. 默认不执行重启、退出、杀进程、停用 MCP、切换代理、改路由、安装依赖、改计划任务、改配置、发送消息、恢复/归档任务或重试不确定动作。只有当前用户已明确指定精确对象和动作时才执行相应项，一条消息可同时授权多个清晰对象。
5. 修复若获授权，先做可恢复备份并记录范围；只改授权对象。修复后重新读取实际目标，不以命令返回成功、进程仍存在或界面最后一行文字代替验收。
6. 发现多个可能对象、父子任务、主机或路径时先通过直接元数据区分；仍有实质歧义才报告缺口，不猜测。浏览器同名连接视图不自动等于多个用户配置，按浏览器恢复参考核对稳定连接标识和本次自有标签。

## 分层诊断流程

按以下顺序逐层推进；某层已经足以解释症状时，停止扩大读取范围。

### 1. 冻结任务身份和故障阶段

使用官方任务/会话读取能力核对完整 session ID、host、project、实际工作目录和来源。归档审查必须同时查看 session_meta.id、parent_thread_id、forked_from_id、thread_source 和工作目录；绝不按相同短 ID 前缀归并主任务与子任务。

把症状归入一个主要阶段：索引加载、SQLite 读取、rollout 历史读取、app-server 排队、WebSocket/TLS/代理、MCP 启动/工具列表、用户任务执行或归档写入。记录观察时间，区分当前回读、历史日志和推测。

### 2. 会话索引层

只读解析当前索引文件的 UTF-8 文本和每行 JSON 结构，统计总行数、无效行、重复完整 ID、最新/最旧时间和引用路径。不要回传整行正文。

- 无效行或重复 ID 说明索引卫生问题，不等于会话正文丢失。
- 索引行数、归档数和 SQLite 线程数可以不同；先报告差异，不做自动去重。
- 一旦出现编码异常、截断行或重复 ID，保存精确行号和脱敏错误类别；不要删除、重排或手工补写索引。

### 3. SQLite 状态层

以只读连接检查实际 state_*.sqlite 的文件元数据、锁/WAL 状态、PRAGMA integrity_check 或 quick_check，以及必要的线程总数、active/archived 计数和表结构。不要导出消息正文或完整历史。

- 完整性为 ok 只说明 SQLite 结构可读，不证明 app-server、索引或 rollout 文件可用。
- SQLite 与索引不一致时，分别报告两个事实，不以任一方覆盖另一方。
- 活跃 WAL 期间不要把单个数据库文件当作一致备份；若获授权修复，使用应用安全的在线备份，并把备份、修改和回读分开记录。

### 4. Rollout 历史路径层

按索引或数据库给出的精确 rollout 路径只读核对是否存在、类型、大小、更新时间、父目录和路径格式。重点区分普通路径、UNC、扩展路径（例如以 \\?\ 开头）、旧工作目录和缺失组件。

- 路径不存在只能证明当前引用不可读取，不能单独证明会话或用户消息丢失。
- 路径存在也不能证明内容可解析；只读取最小的会话元数据或尾部状态，不整段回传 JSONL。
- 不通过近似文件名、日期副本或另一个项目的同名目录补链；候选超过一个时失败关闭。

### 5. app-server、MCP 和进程层

只读盘点 app-server/桌面端的进程路径、版本或哈希摘要、PID、启动时间、数量、CPU/内存趋势和子进程树；比较当前进程启动时间与配置变更时间，识别“旧进程仍持有旧配置”。

对 MCP 逐项记录是否启用、启动命令是否存在、工作目录是否存在、stdio 启动/握手/工具列表是否超时，以及失败属于路径、权限、依赖、进程退出还是网络。命令行和环境变量只做脱敏存在性检查。

对 Docker MCP、docker mcp gateway、Node.js 和 Python 子进程分别统计数量和父子关系。重复的 gateway、工具进程或预热任务可能造成进程风暴和队列延迟；不能因为进程存在就判定服务健康，也不能因为客户端自动重试就盲目再开一轮。

同时检查 app-server 的任务队列、WebSocket prewarm、线程启动和 MCP stdio 启动日志的时间顺序。不要把项目代码、模型算力或网络当作默认根因。

### 6. WebSocket、TLS 和代理层

将网络证据拆成：本机代理监听与系统代理设置、代理到出口的 TCP/DNS/路由、TLS 握手与证书/SNI、WebSocket/HTTP 应用层、请求体传输与服务端读取。Windows 分开核对 WinINET、WinHTTP、应用代理和 TUN；Linux 分开核对目标进程代理配置、监听、路由和应用传输，不自动继承宿主机代理。

- Request body read timed out 先按请求体过大、上传过慢或服务端未及时读取排查；分别记录会话累计记录规模和最近一次请求实际回传规模。
- TLS EOF、证书主机名不匹配、代理拒绝和 WebSocket prewarm 超时必须按时间顺序对应，不能用界面“正在重新连接”单独定性。
- 只在用户请求包含网络验证且不涉及账号时，执行最小的公开探针；探针结果只证明该探针路径，不能替代 Codex 会话链路。
- 不修改系统代理、路由、TUN、证书、Clash 配置或重启代理来“验证”假设。

### 7. 归档写入与回读

归档列表和状态默认只读。若当前用户明确授权精确的归档、恢复或重命名动作：

1. 先以完整 ID、host 和当前状态做读回，确认不是前缀、尾随字符或相似标题。
2. 只调用官方任务管理能力，不直接写 SQLite、索引或 rollout 文件。
3. 写入后重新读取同一完整 ID，核对标题、archived 状态、host 和项目归属。
4. 写入返回超时、连接中断或状态未知时，不重复发送；标记 result_unknown，先用读回或官方对账判断。
5. 重命名成功而归档失败时，保留已改标题并明确旧任务仍未归档；不要创建第二个后继任务。

硬删除、手工数据库修复、路径批量迁移和历史重放不属于本 skill 的默认恢复路径，必须另行授权并保留备份。项目任务接力仍必须由 codex-project-task-handoff 维护唯一交接文件和关闭顺序。

## 结论分级

每一层都使用以下结论词：

- 已证实：存在同一对象、同一时间窗、可重复的直接证据。
- 高度可能：多个相互独立证据指向同一层，但仍缺少一项闭环。
- 尚不能确认：证据只跨层、对象不唯一、时间不对应或存在冲突。
- 结果未知：写入或传输可能已被接受但无法读回；禁止盲目重试。

不要把“索引可读”写成“历史完整”，把“SQLite integrity ok”写成“会话健康”，把“Ready/LastTaskResult=0”写成“业务成功”，把“SSH 登录成功”写成“Remote-SSH 可用”，或把“代理监听正常”写成“远端出口正常”。

## 交付格式

按以下顺序给出脱敏的短回执：

1. 目标、主机、观察时间和授权范围。
2. 各层事实：索引、SQLite、rollout、app-server/MCP/进程、WebSocket/TLS/代理、归档读回。
3. 结论分级及尚未闭环的证据。
4. 已执行动作：默认明确写“仅只读，未修改”；若获授权，列出精确对象、备份和回读。
5. 影响、下一步和禁止盲重试事项。

需要阶段判定、状态字段和修复回执模板时，读取 [分层证据矩阵](references/evidence-matrix.md)；需要授权修复、备份、归档和交接边界时，读取 [恢复与归档回读](references/recovery-and-archive.md)。
