# 发布与完成收据

本参考把复盘结论、源文件变更和受管发布分开。任何一层未完成，都只能报告对应的中间状态。

## 1. 审计和方案阶段

- `audit`：只读归档、规则、skill 源和必要的当前事实；输出范围、去重口径、证据等级和建议落点。
- `plan`：形成最小变更清单、目标文件、测试范围和风险；不写文件、不提交、不推送、不运行真实同步。
- 历史任务的“已完成”只作为历史证据；发布收据必须使用本轮验证结果。

## 2. 源文件验证门

用户明确授权实施后，按 `skill-creator` 的规则完成：

1. skill 名称、description、frontmatter 和 `agents/openai.yaml` 一致；
2. 所有 references 从入口可发现，且没有脚手架占位内容或无主文件；
3. `quick_validate.py` 通过；
4. 新增脚本实际运行并通过代表性测试；纯文本 skill 也要检查模式边界、敏感信息排除和可观察的完成状态；
5. 相关源文件的 UTF-8、`git diff --check`、引用路径和最小行为检查通过。

此阶段完成只能标记 `source_validated`，不能称作已发布。

## 3. 受管发布门

发布按 [主机适配](platform-adapters.md) 分支执行。本机 WSL 默认完成验证、精确提交和推送，再定向预演、安装、哈希回读及新进程发现；不要求 Windows CC Switch 已运行。其他 Linux 主机以其实际受管入口为准。

以下步骤仅适用于 Windows CC Switch：在当前会话已授权提交/推送和 Windows 同步时执行。先读取本机 `cc-switch`，使用它的现行源仓和备份规则，不重写同步脚本。

1. 核对源仓分支、工作树、远端和待提交文件；保留无关脏改动，不将其混入本次提交。
2. 在源仓完成审查和测试后提交并推送；源仓必须满足 `cc-switch` 对 `main` 和远端对齐的要求。
3. 先运行 `sync-custom-skills.ps1 -WhatIf`，确认目标 skill、同步范围和客户端入口；预演失败就停止。
4. 预演通过后才运行真实同步，读取并保留自动创建的备份位置和结果摘要。
5. 回读源仓、CC Switch 安装副本和 Codex 发现目录的文件清单、关键文件 SHA-256、登记来源和启用状态；不得把 CC Switch 内部 `content_hash` 当作文件 SHA-256。
6. 新 Codex 进程通过受支持 `skills/list` 检查安装副本、实际路径、启用状态和加载错误；此检查不需要模型 turn 或持久业务任务。该入口不可用时标记 `discovery_pending`，不能只凭同步脚本返回成功。确需另建业务验证任务时才按对应动作检查授权。

全部通过后才可标记 `published_synced`；三方文件和发现验证也通过后才可标记 `discovery_verified`。

## 4. 失败收据

- 验证失败：保留源文件和测试输出摘要，报告 `source_validated` 未达成的具体门。
- 提交或推送失败：保留工作树和失败原因；Windows 同步和 WSL 正式安装均暂停；推送结果未知先回读远端，不以本机安装替代已推送证据。
- 同步失败：保留 CC Switch 自动备份，不删除备份、不强行重试或改走可视化点击。
- 三方不一致或发现验证失败：停止继续覆盖，报告源仓、安装副本、Codex 入口各自状态。
- 结果未知：不要盲重发、盲重试或把“已接受”写成“已送达/已完成”。

## 5. 最终报告字段

至少报告：复盘范围和去重数量、经验落点、变更文件、验证项目及结果、是否提交/推送、同步备份位置、三方一致性、实际发现验证、当前状态和阻塞。不得粘贴完整日志、内部标识或敏感输出。
