# 业务消费者接入契约

cc-connect 只负责路由、移动通道、凭据、投递账本和脱敏回执。业务项目拥有业务事实、不可变待发送箱、消息内容、发送条件、幂等键和授权边界。中枢不得直写业务数据库，也不得从聊天上下文、网页摘要或标题补全通知事实。

业务自动通知与移动双向协作是两条独立链路：自动通知使用 `direct_feishu` 直接传输，不创建或唤醒 Codex 桌面任务；用户从飞书发起的普通消息继续进入该“项目 + 职责”的固定桌面会话。

## ControlRouteV2 静态登记与运行读模型

公开登记只保存脱敏、可审计字段：稳定 `route_key`、业务项目、`role`、`allowed_event_types`、`registered_sources`、控制目录和固定会话 Hook。运行中的绑定状态、`binding_generation`、会话标识、平台标识、通道凭据、能力令牌、私有路由映射和消息正文只可存在于中枢私有运行边界，不写入 Git、业务仓、Skill、命令参数、环境变量、日志或回执。

每条路由只能对应一个“业务项目 + 职责”。自动数据路由与交易授权路由必须使用不同的控制目录、Hook、私有目标映射和固定会话，不得共享会话键或互相代投。

## 版本化本机接口

中枢控制网关默认仅监听回环地址。业务项目只能通过下列版本化接口访问；Bridge、私有 `/send`、会话映射和平台能力只允许中枢适配器使用。

| 接口 | 行为 |
| --- | --- |
| `GET /v1/routes/{route_key}` | 返回脱敏路由状态、职责、当前及已确认绑定代次、`delivery_mode`、健康结论、队列计数和不透明 `ledger_epoch`。 |
| `POST /v1/delivery-intents` | 只接收路由、来源、事件类型、通知引用、幂等键、内容哈希和过期时间；拒绝正文、任意 URL 和未登记来源。 |
| `GET /v1/deliveries/{idempotency_key}` | 返回登记、移动传输、桌面记录和总体状态；自动直接投递的桌面状态应为不支持或不适用。 |
| `GET /v1/reconciliations/{idempotency_key}` | 认证对账，只返回 `present/absent/unknown`、登记状态和 `ledger_epoch`；`resend_allowed` 恒为 `false`。 |
| `POST /v1/routes/{route_key}/acknowledgements` | 业务项目确认已识别当前 `binding_generation`。 |

### `delivery_mode` 公开枚举

| 值 | 精确语义 |
| --- | --- |
| `direct_feishu` | 业务自动通知的活动模式。中枢异步校验并直接调用私有飞书传输；固定会话不参与。 |
| `session_agent` | 停用兼容或用户明确选择的会话注入实验；不得作为业务自动通知的自动回退。 |
| `disabled` | 自动分发关闭；保留业务待发送箱和两侧账本，不调用 `/send`，也不创建 Timer。 |

每条投递回执固定保存创建时的 `delivery_mode`。业务自动消费者只允许在路由为 `direct_feishu`、状态为 `active`、绑定代次已确认且 `ledger_epoch` 与本地锚点一致时登记；否则失败关闭并保留待发送项。

### DeliveryIntentV1 固定请求

`POST /v1/delivery-intents` 必须且只能包含：`route_key`、`source`、`event_type`、`notification_ref`、`idempotency_key`、`content_hash`、`expires_at`。`notification_ref` 是业务项目定义的受限不透明对象 ID，不能是 URL，也不能承载标题、摘要、正文或深链；`content_hash` 是完整待发送内容的 SHA-256。

- 本机能力令牌只由同宿主受限运行边界提供，不写入 Git、业务配置、日志、任务参数、环境变量、业务数据库或回复。
- 投递查询和对账都必须携带与登记一致的路由、来源和能力证明。
- 确认请求只能提交整数 `binding_generation`；后继代次必须先完成中枢双向验证。
- 业务侧首次读到 `ledger_epoch` 时建立本地锚点；缺失或变化时全局暂停，不能覆盖旧值后继续发送。

中枢按 `(route_key, idempotency_key)` 去重。内容只在投递时从业务项目的受控只读解析器临时读取并在内存中形成；中枢持久账本只能保存哈希、状态、时间、错误类别和不透明关联值。

`DeliveryIntentV1` 不因展示契约升级而改变。业务仓可将受控引用从 V1 扩展到 V2，但必须保持引用是无正文、不透明且可白名单验证的对象 ID。V2 内容哈希应覆盖完整事实、展示字段和最终 `mobile_text`；业务侧预览与中枢解析必须读取同一不可变对象，不能在发送时按新版模板重新生成正文。

## 接入与回读流程

1. 业务项目先读取自身规则与唯一计划，确认事实、事件等级、发送条件、去重和授权；中枢不代为判断。
2. 查询目标路由，核对业务项目、职责、允许事件、来源、`direct_feishu`、活动状态、已确认代次和 `ledger_epoch`。
3. 轻量消费者提交无正文投递意图。中枢完成鉴权与静态校验后原子登记，异步 worker 每轮最多领取一条。
4. 在读取正文和调用 `/send` 前，中枢再次核对路由、业务项目、私有目标、当前绑定代次和交易授权路由隔离。共享会话键、归属错误、代次不一致或目标不可唯一定位时失败关闭。
5. 正文只经受控只读解析器进入内存。内容哈希和过期校验通过后才开始私有 `/send`。
6. 发送开始前的明确可重试故障最多尝试三次；一旦 `/send` 开始，超时、非 200、畸形结果或其他不确定结果统一记为 `delivery_unverified`，不得重发。
7. 业务项目通过投递接口回读结果，并只追加自身回执；不得改写原信封。投递意图 POST 结果未知时只做认证对账，`present/absent/unknown` 均不能自动授权再次 POST。

## OKXnew 首期示例

OKXnew 使用两个隔离显示角色：“OKXnew 消息推送”只接收已确认、高重要级的宏观发布或修订自动通知；“OKXnew 交易授权助手”只处理业务仓允许且由当前用户明确发起的交易授权交互。自动通知不得登记交易、账户、仓位、委托、撤单或执行事件。

- DATA-01 形成合格 V2 核心指标评估后只写不可变 `NotificationEnvelopeV2`；V1 历史、既有回执和未知状态保持原样。来源版本更新但核心值未变、非核心修订、历史补采和缺少连续可比指标时只追加评估/预览，不写外发信封。
- 独立 AUTO-01 是轻量消费者，只提交 `DeliveryIntentV1` 和追加回执，不导入 DuckDB、PyArrow、Parquet 或 WebSocket 数据栈。
- cc-connect AUTO-01 每轮原子领取一条，核对 `okxnew-data-operations`、来源、事件类型、绑定代次和交易授权隔离后直接调用私有 `/send`。
- 自动消息只应出现在“自动推送信息”飞书聊天；不会静默写入桌面任务。用户在该聊天回复后，入站才进入既有“固定会话｜OKXnew 消息推送”，不得新建第三个会话。
- `POST /send` 返回 200 只表示传输层接受；没有可信平台回执时总体仍为 `delivery_unverified`，最终飞书可见性由用户确认。
- 数据监控的只读手机预览直接展示 V2 冻结 `mobile_text`，没有发送、重放或修改能力；cc-connect 对 V2 只做哈希、结构、UTF-8、指标数和 700 字限制校验并原样透传。
- 交易授权助手继续遵循 OKXnew 当前允许的 `simulation` 与 `okx_demo` 边界，不进入自动通知账本。

## 失败关闭边界

- 路由、来源、事件白名单、幂等键、内容哈希、过期时间、业务确认、私有目标或绑定代次不匹配时，在 `/send` 前停止并保留待发送项。
- Bridge 故障只影响依赖 Bridge 的会话换代；固定线程写入冲突只影响 Timer/会话注入。两者都不能单独否定已经通过目标核验的直接飞书传输。
- 旧记录只有在当前用户明确授权、仍未过期、业务账本证明从未登记且中枢对账证明不存在时，才能选一条做一次真实测试；任何已尝试或状态未知的记录永久排除。
- 中枢 `ledger_epoch` 缺失或变化时，业务消费者全局暂停。不得清空状态、从 `absent` 推导重发或连续更换历史信封试错。
- 重绑、实际发送、创建 Timer、修改任务或正式交易仍分别服从当前用户授权与业务仓边界；健康查询不授权这些动作。
