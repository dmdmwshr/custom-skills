# Windows 双链路故障恢复与验收

本流程处理同一 cc-connect 移动聊天中同时出现的两类故障：业务代码自动通知乱码，以及用户普通回复触发固定 Codex 会话后出现模型缓存、运行包、网络刷新、空响应或原始内部错误。两类症状可以同时发生，但属于两条独立链路，必须分别证明根因和修复结果。

## 先冻结错误动作

- 不凭聊天显示名称、单张截图或一个错误气泡重命名、重绑、新建会话或交换私有目标。
- 不重发已乱码、已尝试或状态未知的幂等键；保留业务信封、两侧账本和原状态。
- 不删除或编辑共享模型缓存，不改 Codex 认证、SQLite、索引、会话文件或私有 cc-connect 配置。
- 不把固定会话 Agent 故障误判为 `direct_feishu` 故障，也不把直接投递成功当成固定会话已恢复。

## 第一步：拆分两条链路

| 链路 | 固定路径 | 关键依赖 | 不依赖 |
| --- | --- | --- | --- |
| 代码直接投递 | 业务不可变信封 → 无正文意图 → 中枢校验 → 原生适配器 `/send` → 飞书 | 业务消费者、路由、账本、Windows 正文编码、私有目标 | Codex CLI、Hook、桌面固定会话 |
| 移动入站协作 | 用户飞书普通消息 → cc-connect 路由 → 固定工作目录/Hook → Codex CLI → 回复 | 私有绑定、控制目录、Hook、完整 CLI、模型服务网络 | 自动通知信封、直接分发 worker |

先回读路由、项目、职责、实际 `work_dir`、Hook、绑定代次和私有目标隔离。只有这些证据真实不匹配时才进入绑定修复；全部匹配时继续查各自运行链，禁止重绑试错。

## 第二步：修复直接投递乱码

1. 在不调用 `/send` 的测试中，由业务侧按无 BOM UTF-8 写入包含中文、标点和 ASCII 的合成正文，逐字节核对原生适配器读回值。
2. Windows PowerShell 5 必须在 `Console.In.ReadToEnd()` 前设置 `Console.InputEncoding = UTF8`；同时设置 `Console.OutputEncoding` 与 `$OutputEncoding`。只修输出端无效。
3. 字节不一致时在 `/send` 前失败关闭并记为 `transport_encoding_invalid`；不得用真实飞书反复试编码。
4. 通过往返测试后再运行直接投递、幂等、未知不重发和内容不落盘测试。

## 第三步：修复移动入站 Agent

1. 冻结唯一活动 Codex CLI 入口，核对主程序、命令运行器、沙箱辅助程序和随包工具来自同一完整版本；不得借用桌面内置文件拼接。
2. 模型缓存缺少当前 CLI 所需字段时升级完整独立运行包，不删缓存、不伪造字段、不降级共享桌面状态。
3. 使用无业务事实、无凭据探针分别测试直连和 Windows 当前用户系统代理。只有合法且无用户信息的 HTTP(S) 代理端点通过探针时，才把代理限定注入 cc-connect 的 Codex 子进程。
4. `NO_PROXY` 保留回环控制网关以及飞书/Lark 域名；代理不得扩散到业务消费者、中枢网关或全局项目进程。
5. 用一次性只读 Codex 探针证明实际版本能够产生正常最终回复，且不再出现模型缓存或刷新超时错误。内部标准错误只能进入脱敏本机日志，不能原样回发聊天。

## 第四步：识别 SYSTEM 任务可见性误报

- 普通权限下，受任务 ACL 保护的 `SYSTEM/Highest` 任务可能不可枚举。此时 `Missing` 只能解释为“当前视图未发现”，不得直接推导任务不存在或重复安装。
- 非管理员健康工具应返回 `UnverifiedRequiresElevation`。使用管理员只读视图按精确任务身份核对动作、参数、工作目录、SYSTEM/ServiceAccount/Highest 主体、触发器、Hidden、`IgnoreNew` 和运行状态。
- Task Scheduler Operational 日志可证明同一实例持续运行、恢复触发器命中或重复实例被拒绝，但不能替代管理员结构核验。
- 只有管理员视图也证明任务不存在时才安装；已存在时复用精确身份，禁止创建第二个消费者。

## 第五步：精确部署与本机回读

1. 读取业务仓与中枢的规则、唯一计划和 `INTEGRATION_FEEDBACK.md`，确认当前授权只覆盖哪些修改、任务和外发。
2. 回读两侧待发送、在途、登记未知、送达未知、过期、`ledger_epoch` 和绑定代次；保证历史未知项不会因重启回到可领取集合。
3. 完成编码、运行包、启动器和任务脚本测试；升级任务前保存精确 XML 备份和旧版本哈希。
4. 只更新并重启受影响的既有任务；随后核对唯一宿主、唯一 cc-connect 子进程、单一回环监听、实际 CLI 版本、两条路由工作目录与 Hook。
5. 回读业务接口与中枢路由：`direct_feishu`、`active`、代次确认一致、待发送无意外增长、最后错误为空。自动投递的桌面状态为不支持属于正常设计。

## 第六步：真实双向验收

1. 真实外发必须有当前授权，并只选择一条仍未过期、业务账本无登记、中枢认证对账为 `absent/not_registered` 的合格信封；先 dry-run，再只提交一次。
2. `/send` 返回 200 或 `transport_accepted` 仍记为 `delivery_unverified`。同一幂等键不再提交，交易授权路由不得出现该消息。
3. 由用户确认目标飞书聊天中的中文正文正常、没有乱码或错误控制文本；本机传输接受不能代替该确认。
4. 用户在同一聊天发送一条普通回复，确认由既有固定会话产生正常回答，不出现模型缓存、刷新超时、空响应或原始内部错误，也不创建第三条同职责活动会话。
5. 只有“自动正文可读”和“普通回复正常”两项都由用户确认后，才把反馈台账从 `planned` 更新为 `resolved`，并在两仓唯一计划追加脱敏验收结论。

## 收口报告

最终报告必须分别说明：直接投递路由与队列、移动固定会话、Codex 运行包、代理作用域、Windows 任务视图、是否发生唯一真实外发、用户是否确认中文可读与普通回复正常、是否重绑或创建新会话。不得输出正文、凭据、会话键、完整内部错误、私有路径或平台标识。
