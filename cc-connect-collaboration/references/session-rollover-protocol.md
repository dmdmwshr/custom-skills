# CC-Connect 固定会话换代与双向验证协议

仅在 `session_mode=cc_connect_fixed_session` 且用户从桌面端明确要求“为指定 cc-connect 路由创建后继固定会话并重绑”时使用。本协议不处理普通 Codex 开发任务因上下文过长而进行的同项目接力、初始化、重命名或归档；该类请求改用 `codex-project-task-handoff`。本协议不允许按上下文长度、空闲时长、定时器、程序重启或失败重试自动换代。

`desktop_owner_outbound_only` 完全不适用本协议：不得调用 Bridge 或 Management API，不得创建候选 `N+1`、重绑会话、修改计时器、发送或接受“激活新会话”提示，也不得建议 `/new`、创建、唤醒、转移或恢复第二个任务。该模式保留唯一目标 Desktop fixed task，并将所有飞书入站按 `silent_drop` 处理。

## 前提与角色

- 中枢控制网关持有路由私有绑定与 Bridge 适配；业务项目只能通过路由查询接口读取中枢运行账本的脱敏状态和代次，并确认该运行代次。
- 当前活动代次记为 `N`，候选后继代次记为 `N+1`。运行账本在验证完成前记录为 `binding_pending`；这不是 Git 或公开静态登记字段。
- 旧代次只保留为历史，禁止删除、合并、覆盖或继续接收新的自动业务投递。
- Bridge 仅用于受控会话换代和绑定核验，不是 cc-connect `v1.4.1` 的原生飞书主动文本出口；Bridge 不兼容只阻断依赖它的换代，不得扩大解释为全部外发不可用。

## 状态与幂等边界

- 公开路由接口或静态登记中单独出现的 `active` 与 `dispatch_ready=true` 只表示路由或派发标志，不证明 Bridge 已就绪、同源链完整、候选已产生可验证响应、用户已看到回复或业务已确认新代次。只有本协议全部门禁通过且最终回读一致后，中枢运行账本的 `state=active` 才表示换代完成。
- `binding_pending` 期间重复收到“激活新会话”必须幂等处理：只返回稳定的等待态，说明仍缺少哪些门禁；不得重复创建候选、调整或创建 cron、扫描业务来源、推进水位、恢复自动投递或改写旧代次。
- 归档任务和历史运行记录只证明曾经执行，不能计为活动自动化定义。创建、更新或去重 cron 前，必须按稳定自动化 ID 回读当前活动配置、状态、目标、计划和所有者；同一业务结果存在两个活动触发源或所有者不明时失败关闭，不新建定时器试错。

## 受控流程

1. 核对指定路由的 `session_mode=cc_connect_fixed_session`、路由唯一、职责匹配、实际 `work_dir` 精确等于对应控制目录、无未处理的候选代次，且中枢 Bridge 兼容性检查通过；`CC_PROJECT` 只校验项目别名。若为 `desktop_owner_outbound_only` 或任一条件不满足，立即停止，不执行任何换代 I/O。若需判断定时器是否唯一，只认当前活动自动化 ID 及配置，不认归档运行记录的数量。
2. 使用中枢受控 Bridge 创建并切换候选会话 `N+1`，记录脱敏候选关联值和运行代次；不要改写旧会话或私有配置。若旧会话位于中枢根目录，先由用户显式指定项目与职责完成一次性初始化，再从正确控制目录创建候选；不能直接把根会话提升为活动路由。
3. 请用户在原移动聊天发送一条普通“激活新会话”消息。不要要求 `/new`、清空上下文或发送测试消息。
4. 按以下五项证据顺序回读，并在脱敏验收记录中分别标记：
   1. 候选会话职责、项目和路由与预期一致；
   2. 候选的实际 `work_dir` 精确等于对应控制目录，受审 Hook 与项目身份一致；
   3. 存在新鲜、可追溯的同源链：只从受控 Bridge/Management API 的只读回执取得移动入站关联、cc-connect 绑定和候选 Desktop target 的对应证据，并与运行账本代次相符；若当前适配器没有暴露可核验的同源或新回复关联元数据，本项保持 `unverified`，不能由标题、时间接近、公开 `active` 标志或用户确认补足；
   4. 候选会话已产生可验证响应，且用户在原移动聊天明确回复“已看到回复”；不能用 `active`、`dispatch_ready=true`、Timer accepted 或传输接受推定这一项；
   5. 业务项目已确认 `binding_generation=N+1`，并回读登记的唯一自动化所有者；若为 `cc_connect_cron`，唯一 `reuse` cron 的目标必须仍指向已确认代次，若为 `none` 则明确没有触发同一业务结果的其他定时器。
5. 五项证据齐备后，先受控提交 `N+1` 的状态转换，同时保持自动投递暂停；立即通过 `GET /v1/routes/{route_key}` 和当前活动自动化配置回读运行状态、当前/已确认 `binding_generation`、`ledger_epoch`、唯一自动化所有者与目标、队列计数和未知投递回执。只有这些事实与验收记录一致，才把运行账本的 `state=active` 视为完成、解除候选状态并恢复自动投递。写入或回读超时、缺字段或结果未知时，逻辑状态保持 `binding_pending/result_unknown`，自动投递继续暂停；只继续读回，不重复提交状态转换。

## 失败与回退

- 任一步失败、超时或证据不完整时，保留 `N` 与候选 `N+1`，中枢运行账本维持 `binding_pending`；业务待发送项保持待发送或可重试，不投递到候选会话。
- 只有用户明确取消或回退时才改变候选状态；回退目标是已验证的旧代次，且不删除候选历史。
- 桌面侧栏未即时显示新会话时，只提示用户自行刷新桌面端；不得强制关闭应用、修改共享 Codex 状态或伪报完成。
- `binding_pending` 期间再次收到相同或等价的激活请求，继续只返回稳定等待态；不得把重复入站当作新的确认，也不得因此重复候选、cron、扫描、投递或水位操作。

## 验收记录

在中枢脱敏账本记录路由别名、旧/新运行代次、候选状态、五项验证结论、时间和错误类别。不得记录会话键、平台用户标识、消息正文、凭据或完整私有路径。

Management API 的 `/sessions` 只允许在当前活动集合中捕获唯一候选会话，且必须同时核验路由职责与实际工作目录；不得使用 `sessions list` 读取历史消息或把列表顺序当作绑定依据。候选对应的 `session_key` 只进入私有路由映射，不进入 Git、参数、环境变量、日志或业务数据库。

## 候选快照与源工作区漂移

本节只约束固定会话候选的静态证据，不创建或更新普通项目的交接文件；普通项目接力仍由 `codex-project-task-handoff` 维护唯一 `PROJECT_HANDOFF.md`（或项目规则指定文件），跨项目问题仍只追加到中枢 `INTEGRATION_FEEDBACK.md`。

- 比对控制目录或候选快照时，只读取项目规则明确允许的受控文本，例如适用的 `AGENTS.md`、公开路由登记、受审 Hook 和版本化契约；私有映射、凭据、`.env`、数据库、日志、缓存、媒体、二进制和大文件只比较允许的脱敏元数据或直接排除。先比较允许的相对路径集合，再将允许读取的文本按 UTF-8、LF 规范化后比较内容；单纯 LF/CRLF 差异不应判定为内容漂移。原始哈希只有在换行规范一致时才可直接比较，不得为了对齐哈希改写用户文件。
- 创建候选前记录分支、提交和脏路径集合；候选创建完成后重新读取源工作区的同一组事实。若期间出现分支/提交变化、文件新增/删除、路径状态变化或内容变化，视为源工作区漂移：丢弃旧比较结果，从最新快照重新完成五项证据核验，不得用混合快照激活、归档或调整 cron。
- 任何无法区分换行差异与真实内容变化的情况都按证据不完整处理，保留候选和旧代次，等待重新核验；不得清理、覆盖或提交用户既有改动。
