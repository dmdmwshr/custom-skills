# 会话换代与双向验证协议

仅在用户从桌面端明确要求“为指定路由创建后继会话并重绑”时使用。本协议不允许按上下文长度、空闲时长、定时器、程序重启或失败重试自动换代。

## 前提与角色

- 中枢控制网关持有路由私有绑定与 Bridge 适配；业务项目只能通过路由查询接口读取中枢运行账本的脱敏状态和代次，并确认该运行代次。
- 当前活动代次记为 `N`，候选后继代次记为 `N+1`。运行账本在验证完成前记录为 `binding_pending`；这不是 Git 或公开静态登记字段。
- 旧代次只保留为历史，禁止删除、合并、覆盖或继续接收新的自动业务投递。

## 受控流程

1. 核对指定路由为唯一、职责匹配、无未处理的候选代次，且中枢 Bridge 兼容性检查通过；任一条件不满足即停止。
2. 使用中枢受控 Bridge 创建并切换候选会话 `N+1`，记录脱敏候选关联值和运行代次；不要改写旧会话或私有配置。
3. 请用户在原移动聊天发送一条普通“激活新会话”消息。不要要求 `/new`、清空上下文或发送测试消息。
4. 依次回读以下证据：候选会话职责与路由一致；移动入站已关联候选桌面会话；候选会话已产生可验证响应；业务项目已确认 `binding_generation=N+1`。
5. 四项证据齐备后，原子地在中枢运行账本将 `N+1` 标为 `active`，解除候选状态，并恢复该路由的自动投递。对同一业务待发送项仍按幂等键去重。

## 失败与回退

- 任一步失败、超时或证据不完整时，保留 `N` 与候选 `N+1`，中枢运行账本维持 `binding_pending`；业务待发送项保持待发送或可重试，不投递到候选会话。
- 只有用户明确取消或回退时才改变候选状态；回退目标是已验证的旧代次，且不删除候选历史。
- 桌面侧栏未即时显示新会话时，只提示用户自行刷新桌面端；不得强制关闭应用、修改共享 Codex 状态或伪报完成。

## 验收记录

在中枢脱敏账本记录路由别名、旧/新运行代次、候选状态、四项验证结论、时间和错误类别。不得记录会话键、平台用户标识、消息正文、凭据或完整私有路径。
