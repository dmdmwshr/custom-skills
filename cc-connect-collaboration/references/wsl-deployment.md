# WSL 原生部署

仅当实际目标是 WSL 时采用本节；Windows 专属路径、CC Switch 发布和任务计划示例不作为 WSL 默认入口。

- 源码位于 `/root/workspaces/cc-connect-operations`。本机 `CODEX_HOME=/root/.codex`；Windows 与 WSL 状态隔离，不复制认证、数据库、索引或会话历史。
- 复用已有 `codex-cc-connect.service` 与原生 cc-connect；网关使用 `cc-connect-operations.service`，只监听 `127.0.0.1:8765`。两个服务不创建扫描定时器，不调用 Windows 可执行文件。
- 配置分属 `/etc/codex-cc-connect` 与 `/etc/cc-connect-operations`；运行数据分属 `/var/lib/codex-cc-connect` 与 `/var/lib/cc-connect-operations`；版本化网关发布位于 `/srv/cc-connect-operations/releases`。私有文件权限 0600、目录 0700，日志只含脱敏状态。
- `--staging` 使用独立 staging 账本，强制无令牌、无来源解析、无派发。其新 epoch 不能冒充生产账本。生产入口必须先存在一致迁入的账本，不自动建空生产库。
- Linux 直送仍由私有子进程接收 UTF-8 stdin，经独立绑定与项目校验后访问受限 UDS。200 且合法 `status=ok` 才记传输接受；发送开始后异常全部未知且不重发。X 直送只用 A 模式门禁；新扫描仍必须有唯一 Desktop 所有者和 heartbeat 证明。
- 切换前精确停止旧桥接并暂停旧 X 自动化，确认业务锁空闲，取得受限一致性备份与回读。缺失停机、备份或受支持会话迁移入口时保留关闭派发的准备态。不能通过更改数据库制造已迁移证明。
- 安装与更新使用 WSL 源仓的 `scripts/publish_wsl_skills.py`，先 dry-run，校验 Skill 结构后 `--apply`、`--verify`；记录提交、源修改状态和文件哈希，再由新 Codex 会话验证发现与加载。不编辑安装副本，不要求 Windows CC Switch 才能发布 WSL 更新。

## 用户明确批准的唯一 Linux 接替

只有用户已批准新固定会话接替时才采用本分支；不因旧任务无法转移而自行创建替代任务。复用负责 X 的任务已通过产品创建和初始化的唯一候选，回读目标主机、完整工作目录、模型/思考与每小时计划，再绑定 PAUSED heartbeat。保留旧聊天历史，禁止复制 Codex 认证、数据库或历史。旧会话 ID 转移不再是该授权分支的条件；新任务创建、入队或初始化均不等于接管完成。

- 中枢只负责原凭据、投递目标、绑定代次、网关账本和受限出口；X 任务负责浏览器、X 账本、唯一固定任务与实际周期。用户另行批准扩展失败后使用已有 Linux Playwright 组件时，由原唯一 X 固定任务执行，不增加常驻扫描者，不把该授权推广到其他项目或任务。
- 先通过产品入口精确暂停旧 X heartbeat，确认旧扫描入口退出、双锁和 finish_pending 空闲，再精确停止旧桥接并取得同一停机窗口中的 X/关联中枢一致备份。检查完整性、哈希、epoch、幂等、水位和未知记录。回执必须区分入队、承接、预检、停机与备份；旧运行快照不能代替新鲜停机证明。证据缺失仍关闭新派发，不自行恢复旧扫描造成双写。
- 导入包内 Windows 路径、旧同源回读与 A 模式 marker 都是历史资料，先逐文件核验来源哈希与私有权限。原目标哈希和绑定代次必须匹配，未知消息不重发。旧配置哈希过期时不得简单更新 marker 来制造已通过证明；采用 Linux 独立出站证明，明确保留原出站目标而非声称 Windows p2p 会话已迁移。
- 使用项目受控准备器生成独立 0700 候选目录、0600 文件。X-only 配置只包含原 X 项目，平台块、允许名单和凭据保持原字节；原六路绑定保留，其余连接不得随服务启动启用。网关用 `--only-route x-monitor-notifications` 同时限制来源 capability、解析器与 worker 路由。Desktop 实际目录与中枢出站控制目录分别登记，飞书入站仍 silent_drop。
- Linux 出站证明的 prepared 状态不能通过发送门禁；生产提交必须在停机、双库备份、账本与新所有者回读齐全后完成受控事务。A 模式每次发送只校验私有配置、目标、代次、完整性和入站抑制，不把浏览器或 heartbeat 健康塞入每次发送；新扫描的唯一所有者和周期门禁继续由 X 负责。
- Hook 信任约束各自交互会话；X-only 出站不要求为通过验收而启用其他五路交互业务。自然投递的传输接受、用户可见与业务处理分别验收；离线测试、进程运行和准备态发布不能写作真实送达。Linux heartbeat 由负责 X 业务验收的原任务在门禁满足后恢复，中枢不得提前启动。

需要跨主机协作时优先使用当前产品任务消息工具。未暴露该工具时，可核对目标主机已安装 CLI 是否支持 `codex queue`，用官方任务元数据唯一定位精确 ID 后入队；不得猜 ID 或以任务标题的模糊匹配发送。CLI 成功仅表示入队，必须等待原协调任务的实际回执，不能靠新建平行任务或改内部状态强制执行。

## 主控统一多项目切换

用户建立总控并下发工作包后，各原项目任务继续作为各仓唯一主写者；原有停机/执行请求服从最新阶段放行，不因旧请求已入队而自行执行。可以继续源码、合成测试、独立逻辑提交和候选发布；正式停写、导入、服务启用及验收外发分别按当前用户授权和主控阶段执行。完整协调任务身份只放私有引用，公共台账不输出 ID。

- 先按 Git 清单保全 Windows、WSL 与额外候选副本，记录哈希、差异和已有改动归属；额外副本不作为第二网关。保护未归属改动，不能把整个脏工作树冒充本轮独立成果。
- 多路候选必须逐条明确白名单；保留原平台块、凭据、允许名单和绑定代次。只转换已识别的 Windows 启动路径、CODEX_HOME 与 PATH，未知启动选项失败关闭。X 保持 outbound-only/silent_drop，OKX 授权助手不取得自动通知能力，未绑定路由不被启用。
- Linux 按来源读取 capability：X 与 `okxnew-data-service` 独立鉴权。OKX 只读 systemd 提供的受限运行时凭据，不能用其配置整体覆盖 X 配置或回退为 X token。显式路由选择必须同时限制 API 准入、解析器及 worker。
- 只有用户明确批准时，源主机 SQLite `rw/query_only` 连接才可在正常 close 时自行归并 WAL；这不是无物理写入的只读检查。保全阶段指纹、全表类型化摘要、完整性/FK、水位、冻结字段、epoch 和未知状态；失败不发布部分清单，不显式 checkpoint、删旁车或自动重试。总控的七库共同停写证明不能由 X/网关两库备份成功替代。
- 正式导入必须 pin 完整配对 manifest 哈希并验证双方快照，拒绝覆盖、重复导入与重新生成 epoch。多目录成对导入采用停写门禁、持久日志和原子提交标记时，应说明其可恢复事务语义，不能声称两个文件 rename 天然原子。两侧写入者在开库前检查提交标记，并在整个运行期间持有共享事务锁；仅 ExecStartPre 检查不充分。任一侧尚未接入时保持关闭。
- 回滚只处理本事务创建且未变更的目标；出现新业务写入、旁车或外来目标时停止并对账，不能覆盖 Linux 新数据或重新开启旧 Windows 写者。准确实现与候选门禁见项目 `docs/PAIRED_MIGRATION_IMPORT.md`，执行状态仍只写唯一项目计划和总控机器回执。

## X 启动前失败的受限标记恢复

- 异常EOF留下的X标记不能因进程退出、锁释放或超时而手删。仅有真实证据证明尚无受管driver/client、业务标签、acquire/scan/send且无lease/finish_pending时，才使用中枢现有受控恢复入口；业务已开始或结果未知的轮次仍归原owner两阶段finish，不适用本分支。
- 恢复消费不可变失败原件、固定入口的新鲜health原始捕获、官方owner完成idle、当前实例和精确标记哈希；health无生成时间时明确使用捕获时间，不伪造业务时间。入口在activation排他锁与pair共享锁下核对精确进程及标记身份，原子归档保全原inode/字节，不重启服务或改账本。准确参数以项目 `docs/PAIRED_MIGRATION_IMPORT.md` 为准。
- API对象的VM求值、元数据检查、业务方法调用与受管driver创建分别记账。晚到更正使用独立回执关联原SHA；仅元数据对象须由原owner一次纯内存废弃并回读，官方idle晚于废弃。已实际归档后只重新验证事实与当前静止状态，不恢复旧标记、重复apply或追改原接受结果。历史复制的marker字段不能替代实际文件状态；存在后继标记必须保留。
- 不同初始化失败须保留其原始schema、阶段和调用次数，不套用旧错误类型。Timer注入失败的窄分支须同时核对owner补充绑定的原失败SHA、当前boot/发布、精确marker和无后续launch；旧health过期时只在执行前协调一次真实固定入口观察，记录实际执行者，不能改mtime。
- 控制脚本升级默认逐字稳定。经明确审阅的guard单文件修复仅走既有升级器的精确delta分支：cc发布相同、X文件集合相同且只有guard变化，审阅回执和限时phase均绑定完整delta；先受控归档标记，再在原网关唯一停启窗口切X链接。其余控制脚本、账本、配置、epoch和历史投递不变。
- 首次增加同CUA固定control client时，只使用既有升级器另一个明确受审模式：精确新增client和修改guard、其余既有文件逐字不变，审阅及phase绑定旧新manifest和两项完整delta；不复用guard单文件许可，也不授权后续任意client更新。默认模式继续拒绝client增删改。候选中的脱敏fixed error只能证明错误格式，不能证明业务未发生；已启动可变控制须保留unknown并禁止同动作重试，finish开始后关闭其他可变控制。
- 恢复成功不自动授权重试、补发或恢复heartbeat。下一runtime仍由原X开发任务单一协调；中枢不另行向owner发送并行启动指令，旧失败与更正时序完整保留。

## 多路业务启用与固定线程

### X 控制阻断时的独立投递准备

用户要求修复全链路时，继续完成不依赖浏览器的投递检查；CUA 未就绪只阻断新扫描和尚未完成的 X 激活，不阻断已授权的只读准备。中枢不另起浏览器或扫描者。

- 先用项目现有 X A-mode 校验器核对原目标、绑定代次、配置完整性和 `silent_drop`。通过仅代表本地出站契约一致，不证明平台权限、当前发送能力或真实送达；不得为了校验而重绑、重建连接或重跑已完成的配对导入。
- 需要核验平台时，复用受限配置与现有官方只读适配器；应用凭据及短期认证令牌只在内存使用，禁止从 Cookie 提取。精确原 p2p 聊天 GET 成功证明该应用凭据与该查询可用，不证明发送权限。其他路由的成功回执不能替代 X 本路由证据。
- 应用信息、权限和版本发布分别只读回读。管理 API 查询失败若未取得可解释的脱敏错误，不推断为凭据错误、权限缺失或应用未发布，不反复请求或新增权限试错。确需网页补证时，将精确页面、原目标的私有比对方式、必要非敏感字段和只读动作交给唯一 owner；检查权限管理的发送权限生效状态、版本管理的当前已发布版本/未发布变更和机器人启用状态。只读任务不保存或发布，页面可见也不证明 API 投递成功。
- 回执分开记录本地契约、凭据认证/目标查询、发送权限与版本发布、实际发送调用、官方消息观察、用户可见/已读；没有执行的项目明确未验收。已有未知消息不因补证重发，不发送合成业务探针。
- 候选代码和合成测试可独立准备，但已知激活门禁缺口必须修复后再启用。当前客户端自检要求以已固定版本的完整预期集合为准，不能把部分条目当作全部通过；WSL 当前实例证明复用已有发行版实例身份，不能仅以共享内核启动时间替代。控制失败或未执行自检的回执不能转换为成功 schema。准确契约与执行权限仍以项目当前文档和主控阶段为准。

- 主控分阶段接管时，使用中枢已审查的 `manage_linux_activation.py` 形成私有绑定计划、准备启用包、消费真实 systemd 凭据、arm、只读 binding-probe 和 enable；对应受控回滚为 rollback-enable、rollback-arm。准确参数与回执格式以项目 `docs/LINUX_ACTIVATION.md` 为准，不手改 prepared/committed 或 enabled 标志替代受控事务。
- 双向路由先按完整 Linux cwd/职责通过产品查找：复用唯一已初始化线程，不存在才按用户授权创建，歧义先解决。授权助手、宏观通知与分类通知保持独立；X 复用其唯一 Desktop owner，继续 silent_drop，不接入双向固定线程适配器。Windows ID、相同标题和业务仓根目录开发任务都不能替代控制目录线程证明。
- 使用 cc-connect 官方 cmd 扩展固定恢复线程时，必须保留原权限模式、模型和 effort，以实际 cwd、精确私有目标及代次约束调用；CC_PROJECT 只作可选一致性核对。正文只经原始标准流，不读写 Codex 数据库/JSONL，不用包装器绕过 Hook 信任或恢复其他路由。产品初始化、Hook 信任和实际入站回复分别留证。
- arm 只允许生产 API 与既有入站连接就绪，worker 和私有发送入口仍关闭。先真实消费 systemd 的独立来源凭据，再用所属来源 GET 核对代次/epoch，交叉 token 必须拒绝；不把文件存在或合成测试写成真实解密/鉴权成功。只读核验不调用 /send、不初始化空账本/路由行、不修改业务确认代次。
- enable 在网关停止的精确窗口复核完整私有配置、原子提交标记、账本确认、产品职责和限时回执，最后才开放 dispatcher；启动后可能处理既有可派发意图，因此实际启动也须属于主控业务阶段。未知投递不重发，授权助手仅只读验收，不新增主动通知测试。X 扫描恢复仍由其原任务和主控通过产品入口负责。
- 配置事务保留完整原字节和 before/after 哈希，部分提交无匹配启动标记则保持失败关闭。回滚只恢复本事务仍匹配的配置，并要求精确停机、owner 静止和无未完成 X 标记；先失效启动标记，完整恢复后再发布原标记。不得回滚业务账本、覆盖新投递状态或重启旧 Windows 写者。


## 当前 Linux 业务恢复备份与入站参数

- 迁入时的原配对快照不能覆盖后续新业务。业务验收后需要当前恢复点时，先核对既有备份CLI的主机限制；Windows专属入口不能直接替代Linux。复用中枢已有备份核心与受限Linux入口，精确命令以 `docs/PAIRED_MIGRATION_IMPORT.md` 当前恢复备份节及实际候选handoff为准，不新增常驻备份框架，不重导、不重建epoch、不重放未知。
- 当前备份由主控另选正常空闲停写窗口：原X两阶段finish/guard清理、产品暂停原heartbeat与owner idle、业务方停新生产者、精确停网关/bridge，再按新鲜plan及停写回执备份当前双库、策略、代次、pair/epoch及最小恢复配置。准备态只读元数据即可；不得为了准备开正式X库，也不把该备份变成X双流或原heartbeat启用前置。SH配对锁只隔离管理事务，必须另验无写者和逐阶段一致性；失败保留原尝试，不另选目录自动重跑。
- 恢复服务沿既有配置和批准范围，先bridge再gateway，分别回读唯一进程/回环/原路由；业务方恢复原生产者及计划状态。恢复可处理合法新pending，不能要求全库pending为零，也不能借恢复补发历史未知。备份完成不自动授权删除旧主机或覆盖新账本。
- 固定入站使用产品默认模型时，绑定的空模型表示不传模型参数，不能生成 `--model None` 或擅自选一个模型。保留原权限、effort、cwd和精确线程；用合成argv覆盖默认/显式模型及首次/续接，再单独做真实入站。Hook信任须结合祖先项目信任、精确Hook状态与当前定义，不能仅凭缺少直接cwd配置项或文件存在就下结论；不创建全局通配信任或关闭门禁来验收。
