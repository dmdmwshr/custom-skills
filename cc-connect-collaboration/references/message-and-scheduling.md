# 消息与定时协作

## 投递前检查

1. 目标路由为 `active`，且职责与消息内容相符。
2. 业务仓已产生可投递的事实或待发送事项，并已经完成自身去重和权限判断。
3. 消息不包含秘密、原始会话内容、账户交易信息或不应跨项目扩散的数据。
4. 当前操作确实得到用户或业务规则授权；不要用“测试消息”占用真实通道。

使用 cc-connect 发送时，优先显式指定项目和目标会话；长文本从标准输入传入。发送后只记录脱敏投递结果和幂等键，不保存或复述完整消息内容。

## 固定会话代发与人工回退

- 默认通过 `/timer/add` 向目标固定会话注入不透明任务；会话使用 Luna low 和固定 hook 读取受控引用，只输出最终通知，由同一 ReplyCtx 自动回发原飞书会话。
- 会话不得调用 `POST /send`。中枢直接调用受限 UDS `POST /send` 只允许在用户明确授权的人工直接回退中使用；同一幂等键不得同时走两条路径。

- 受限 UDS 的 `POST /send` 是已验证的人工主动文本出口，但不是自动业务通知默认路径。Bridge 与 Management API 也不是本链的自动通知出口。
- 中枢通过私有 `route -> project/session_key` 映射解析目标。每次请求都必须显式指定路由与目标，不得选取“第一个会话”或依赖列表顺序。
- 人工回退的消息正文只从标准输入或进程内存进入发送调用，不写命令参数、环境变量、Git 文件、日志、能力映射或业务数据库。
- `transport_accepted` 只代表 cc-connect 传输层接受请求；无可信平台回执时仍记为 `delivery_unverified`，不得称已送达或已读。
- Management API 的 `/sessions` 只用于当前活跃集合中的唯一候选捕获，不用 `sessions list` 读取历史；发现零个或多个候选都失败关闭。
- 以 Timer 接受、一次性发布权领取、会话最终回复和飞书送达未知分别回读；不得把会话最终回复再复制为第二条直发消息。

## 宏观消息的最小信封

```text
【OKXnew 消息推送】宏观发布更新
结论：<发布/修订/未获取到的简短结论>
影响：<对监控或分析的影响；没有则写“无”>
下一步：<已完成的落库、补采或等待动作>
需要你决定：无 / <唯一明确问题>
```

消息的事实必须来自业务仓的规范记录。中枢不从标题、网页摘要或聊天上下文自行推断数值，也不负责把未经验证的数据升级为通知。

## 选择定时器

| 场景 | 选择 | 会话策略 |
| --- | --- | --- |
| 需要固定聊天的上下文判断、调整下一轮任务 | 桌面端该固定会话的计划任务 | 保留原会话 |
| 精确时刻触发受控提示词 | cc-connect `cron --prompt` | `reuse` 适合连续职责；`new-per-run` 适合隔离任务 |
| 系统启动、登录或守护进程恢复 | Windows 计划任务/服务 | 与聊天会话无关 |

创建任何定时器前，先手工运行同一提示词并核对范围。记录人类可读描述、路由别名、目标结果、时区、去重键、超时和静默策略；不要登记私有会话键或消息正文。

## 去重与失败

- 同一“业务事实 + 路由 + 发送目的”只能有一个活动定时器和一个待投递项。
- 定时任务先解析并校验业务内容，再以随机 nonce 原子领取同一去重键的一次性发布权；领取失败时安静结束。仅 Timer `fired` 但没有 claim 不得标记为已发布。
- 发送没有可信回执时标记 `delivery_unverified`；未知送达不得自动重发。只有能证明传输前失败且业务规则允许时才可保持原待发送项可重试，不制造新的待发送副本。
- 关机、未登录或桌面应用未运行只说明本轮不可执行；除非用户或业务规则指定，不把这种环境状态转换为移动端报警。

## 本机私有边界

- 运行时 ACL（访问控制清单）文件、能力令牌和路由映射不得进入 Git、命令参数、环境变量、日志、回复或业务数据库；只存在于受限本机运行边界。
- `AUTO-01` 的控制网关与投递 worker 必须在同一宿主机运行，通过受限 UDS 交接；不要把私有映射或能力令牌跨主机分发。
