# CC-Connect 移动协作

将 `cc-connect-operations` 作为桌面端协作中枢，而不是业务代码仓。每个“业务项目 + 职责”拥有一条独立、持久的固定会话流；中枢只承载会话、通道、启动和投递，业务规则、数据与授权仍属于原业务仓。

## 核心边界

- 固定会话位于中枢项目下的控制目录，例如 `projects/<业务项目>/<职责>`；不要把多个项目或职责合并到同一个聊天上下文。
- 一个 cc-connect 进程可以托管多个独立项目。每条控制路由必须有稳定的公开别名、独立工作目录和独立会话策略。
- `C:\\Users\\12070\\.codex` 是唯一共享 Codex 状态目录。不得复制、迁移、合并或改写其认证、数据库、索引或会话文件。
- 私有通道凭据、会话键、会话正文、Cookie、令牌和账户信息永不进入业务仓、公共登记表、Skill、日志或回复。
- 移动消息不扩大业务仓已有权限，尤其不能直接变成真实交易、正式发送、凭据访问或不可逆数据删除的授权。

## 先确认目标与现状

1. 确定业务仓、职责、预期移动通道和操作类型：新建、迁移、发消息、配置定时，或只读核验。
2. 读取业务仓的 `AGENTS.md` 和唯一计划，确认该职责允许处理的范围；再读取中枢项目的 `AGENTS.md`、唯一计划和脱敏控制登记表。
3. 检查是否已有同职责控制路由、桌面固定会话和定时器。发现重复时先停止，不创建第二条流或并行定时器。
4. 只读请求只能报告状态。新建路由、变更私有绑定、创建定时器、修改 Windows 任务或发送消息，分别需要当前用户针对该动作的明确授权。

需要字段、状态转换和验收口径时，读取 [固定会话路由契约](references/fixed-session-contract.md)。

## 创建或绑定一条固定会话

1. 先在公开控制登记表准备一条路由：业务项目、职责、目标业务仓、中枢工作目录、状态和会话策略。公开表只放脱敏别名，绝不写真实会话标识或平台用户标识。
2. 在中枢项目创建对应控制目录，并写清该职责能做什么、必须回到哪个业务仓读取规则、以及与其他职责发生文件冲突时如何停下。
3. 用户明确要求创建或迁移时，在 `cc-connect-operations` 桌面项目中创建或识别一条专用固定会话；标题使用“固定会话｜<业务项目> <职责>”。它是独立上下文，不是业务仓已有聊天的物理搬迁。
4. 先备份私有配置，再使用中枢项目的受控迁移工具，只改已经逐项核对的项目名、工作目录和会话绑定引用。平台块、允许名单、凭据和既有历史必须原样保留。
5. cc-connect 当前没有离线预建移动会话的命令。没有首次入站消息时，路由应显示为 `awaiting_first_inbound`，不要为测试而自发消息或伪造会话。
6. 首次入站后，通过脱敏校验确认：路由别名、工作目录、持久会话策略、通道加载、唯一进程链和预期固定会话都一致。全部满足后才标记为 `active`。

不要用会话清理或合并命令处理迁移历史；旧会话应保留为未绑定历史，除非用户明确批准精确清理。

## 移动消息协作

只向已核验的活动路由发送业务需要的消息。多行内容优先从标准输入传入，避免转义错误；消息必须指定目标项目，必要时再指定目标会话，不能依赖“第一个活动会话”的偶然选择。

推荐消息结构：

```text
【业务项目｜职责】主题
结论：一句话说明当前结果。
影响：对数据、交付或决策的影响；没有则写“无”。
下一步：已执行或待执行的动作。
需要你决定：无；或给出一个明确选项。
```

- 不发送凭据、会话标识、原始消息正文、账户/订单信息或未经业务仓授权的外部内容。
- 不发送“链路测试”或重复健康提醒。只有用户明确要求实际投递，或业务产出的待发送事项已达到其发送条件时才投递。
- 宏观、行情等业务消息由业务仓完成来源判定、去重、持久化和发送条件判断；中枢只按已核验路由投递并回读投递结果。
- 发送成功不等于业务处理成功；没有可验证回执时只报告 `delivery_unverified`，不得编造已送达。

消息模板、投递确认和定时选择规则见 [消息与定时协作](references/message-and-scheduling.md)。

## 定时唤醒的三层选择

| 目标 | 使用方式 | 要点 |
| --- | --- | --- |
| 唤醒某条 Codex 固定会话继续既有上下文 | 桌面端该会话的计划任务 | 先手工验证提示词；桌面应用未运行时不能声称已执行。 |
| 到精确时点执行一条 cc-connect 路由任务 | cc-connect `cron` | 指定路由、会话策略和幂等提示词；同一业务结果只保留一个有效定时器。 |
| 保证移动桥接进程生命周期 | Windows 计划任务/服务 | 与消息内容无关；改动前先核对任务身份，未经授权不得启停或重建。 |

- 需要持续上下文时使用 `reuse`；一次性、相互隔离的任务使用 `new-per-run`。两者都不是“开机自启动”的替代品。
- 先手工验证提示词，再创建定时器；明确运行窗口、超时、静默策略、失败后的重试边界和去重键。
- 不把轮询当作告警源。桥接因关机、未登录或桌面应用未运行而不可用时，记录可解释状态，等待下一次允许的唤醒；除非业务规则或用户明确要求，不额外发送报错或警告。

## 从业务仓迁移到中枢项目

1. 盘点旧会话、旧路由和既有定时器，只记录脱敏别名与归属，不读取消息历史。
2. 在中枢中创建或识别替代固定会话，并先完成新的路由验证；不要先解绑旧路由。
3. 备份私有配置，精确更新绑定，并回读结构化健康结果。任何字段无法唯一定位、平台块出现变化或验证失败时立即恢复并停止。
4. 新路由健康后，才把已有桌面计划任务或 cc-connect 定时器改指向新固定会话；同一时刻只能保留一个会触发同一业务结果的定时器。
5. 旧会话保留历史但不再接收新工作。报告迁移完成、旧路由状态、定时器去重结果和仍需用户决定的事项。

## 健康判断与报告

使用中枢项目提供的脱敏核验脚本、任务状态和唯一进程链进行回读；不要打开私有配置或会话数据库来“人工确认”。

- `active`：路由、工作目录、持久策略、通道和进程链均匹配。
- `awaiting_first_inbound`：公开路由已准备，但尚未由真实入站创建会话。
- `binding_mismatch`：公开登记、私有绑定或固定会话归属不一致；停止迁移与发送。
- `bridge_not_running`：桥接未运行；不擅自重启，除非当前用户已授权该任务操作。
- `desktop_app_unavailable`：桌面固定会话计划任务不能执行；不伪报完成。
- `delivery_unverified`：没有可验证回执；不得称“已送达”。

最终用自然中文说明：路由、会话、通道、定时器分别是否就绪；本次有没有实际发送或改动；以及用户是否还需要作出一个具体决定。不要输出私有路径、原始配置、完整会话标识或消息正文。
