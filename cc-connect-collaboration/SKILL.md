# CC-Connect 移动协作

将 `cc-connect-operations` 作为桌面端协作中枢，而不是业务代码仓。每个“业务项目 + 职责”拥有一条独立、持久的固定会话流；默认由定时器将不透明任务注入固定会话，固定会话以 Luna low 读取受控引用并只输出最终通知，由 cc-connect 同一 ReplyCtx 自动回发原飞书会话。

## 与普通项目任务接力的互斥边界

- 用户说当前普通开发任务轮次太多、上下文太长，希望总结项目、创建同项目后继任务、初始化后改名并归档旧任务：停止本 Skill，改用 `codex-project-task-handoff`。不得读取 cc-connect 路由、Bridge 或私有绑定来处理该请求。
- 用户要求替换 cc-connect 已绑定或待绑定的固定会话，并涉及移动入站、控制目录、路由代次、重新激活或恢复自动投递：继续使用本 Skill，不创建普通项目接力任务。
- 只有“换会话”而没有普通项目或 cc-connect 线索时，先用一个简短问题确认对象；未确认前不创建会话、不改绑定、不重命名也不归档。
- 普通任务接力与固定会话换代不得在同一流程中串联，也不得用一个 Skill 的验收状态代替另一个 Skill 的验证。

## 核心边界

- 固定会话位于中枢项目下的控制目录，例如 `projects/<业务项目>/<职责>`；不要把多个项目或职责合并到同一个聊天上下文。
- 一个 cc-connect 进程可以托管多个独立项目。每条控制路由必须有稳定的公开别名、独立工作目录和独立会话策略。
- 即使用户把多个控制子目录添加为同一个 Codex 桌面项目的源目录，活动路由的实际 `work_dir` 仍必须回到各自控制目录。目录本身是路由身份；`CC_PROJECT` 只做项目别名一致性校验，不能选择、替代或修复工作目录。
- OKXnew 的两个用户显示角色固定为“OKXnew 授权助手（非交易授权）”和“OKXnew 消息推送”；两者分别使用独立控制目录、路由和私有会话映射，不使用“数据运营”“策略研究”等泛化名称替代。
- `C:\\Users\\12070\\.codex` 是唯一共享 Codex 状态目录。不得复制、迁移、合并或改写其认证、数据库、索引或会话文件。
- 私有通道凭据、会话键、Cookie、令牌和账户信息永不进入业务仓、公共登记表、Skill、日志或回复。会话正文默认不读取；当前用户明确授权核对指定会话或路由职责时，才可按“最小必要职责核验”读取所需局部证据，且不得复制原文、写入任何持久位置或扩大为全量历史浏览。
- 移动消息不扩大业务仓已有权限，尤其不能直接变成真实交易、正式发送、凭据访问或不可逆数据删除的授权。
- 每条路由必须有独立控制目录、固定 prompt hook 和明确职责；通知 hook 只允许读取已登记的不透明引用，授权助手 hook 不得被写成通知发布 hook。
- 每条路由的 `work_dir` 必须独立维护自己的 `.codex/hooks.json`，仅允许受审的 `SessionStart` `startup`、`resume`、`clear`、`compact` 事件，并通过 `additionalContext` 注入固定职责说明；不得跨路由共享或绕过 hook。
- 自动通知链只允许 `session_agent` 执行；固定会话不得调用 `/send`。启用前必须同时核对项目身份和 exact hook hash，并在设置→Hooks或 CLI `/hooks` 中审核；任何修改后都必须重新审核，审核失败立即停止自动链。
- 业务项目的自动通知消费者应与 DuckDB、PyArrow、Parquet、WebSocket 等重型数据采集栈隔离为独立轻量进程或任务；数据任务只生成不可变信封，消费者只处理脱敏引用、登记状态和追加回执。两者不得同时消费同一待发送箱。
- 中枢必须先完成鉴权和静态校验，再原子登记 `registered_held`，随后才异步检查 Hook、UDS、固定会话和 Timer 健康。业务消费者必须锚定中枢返回的 `ledger_epoch`；epoch 缺失或变化时失败关闭。
- 必须区分“投递意图登记结果未知”和“Timer/会话发布结果未知”。前者只允许认证 GET 对账，既有不确定记录统一进入 `suppressed_unknown`；无论对账结果为 `present`、`absent` 还是 `unknown`，均不得自动再次 POST。后者从 Timer POST 开始即永久禁止自动重建 Timer。

### 用户授权的最小必要职责核验

当当前用户明确要求判断“某个会话实际负责什么”“聊天名称是否与路由对应”“绑定是否串线”或明确允许读取指定会话时，不得只凭显示名称、脱敏健康结论或旧截图推断。可通过官方桌面或 Bridge 只读接口，检查指定对象的实际 `work_dir`、路由/项目归属、受审 Hook、启动职责说明及完成判断所需的最少相关对话。

1. 以实际 `work_dir` 与受审 Hook 职责为最高证据；路由/项目归属次之；聊天显示名称只用于呈现，不能作为绑定事实。
2. 只读取当前判断所需的局部内容，不批量浏览历史、不扫描无关会话，也不把原文、完整日志、会话键或私有配置复制到回复、台账、业务仓或 Skill。
3. 始终排除凭据、Cookie、令牌、账户信息、完整私有配置以及 Codex 数据库、索引和会话文件；不得直接读写这些内部文件。
4. 诊断读取不自动授权重绑、重命名、发消息、创建 Timer、修改任务或改写会话数据；这些动作仍须当前用户分别明确授权。

## 先确认目标与现状

1. 确定业务仓、职责、预期移动通道和操作类型：新建、迁移、发消息、配置定时，或只读核验。
2. 读取业务仓的 `AGENTS.md` 和唯一计划，确认该职责允许处理的范围；再读取中枢项目的 `AGENTS.md`、唯一计划和控制登记表。当前用户明确要求职责诊断时，按“最小必要职责核验”补充实际会话证据。
3. 检查是否已有同职责控制路由、桌面固定会话和定时器。发现重复时先停止，不创建第二条流或并行定时器。
4. 只读请求只能报告状态。新建路由、变更私有绑定、创建定时器、修改 Windows 任务或发送消息，分别需要当前用户针对该动作的明确授权。

## 跨项目衔接反馈

当业务项目发现路由、工作目录、会话、Hook、网关、桌面可见性或投递衔接异常时，先定位并读取中枢根目录唯一的 `INTEGRATION_FEEDBACK.md`；它是人工与 Agent 共用的反馈台账，不是网关 API、自动监控器或自动修复授权。

1. 先读取台账、当前中枢 `AGENTS.md` 和唯一计划，做只读分诊：确认关联项目/路由、类别、预期与实际、影响、最小复现和可公开的证据是否完整。当前用户明确授权路由职责核对时，可按“最小必要职责核验”读取指定会话的实际目录、Hook、启动职责说明及最少相关对话；不得读取凭据、令牌、Cookie、账户、完整私有配置或无关历史，也不得把会话原文写入台账。
2. 需要登记新问题时，只能按台账模板追加 `CCOPS-<报告方>-<时间>` 事实记录；处理既有记录时，只能追加处理记录并按 `new → triaged → planned → resolved | blocked | rejected` 更新，绝不重写报告方原始事实或建立第二个反馈入口。
3. 分诊不构成实施授权。完成分诊后等待当前用户明确授权，才可修复中枢、路由、Hook、网关、桌面项目或业务仓中的对应事项；不得因反馈自动重绑、发送、创建定时器、启停运行任务或改写私有配置、会话数据和 Codex 状态文件。
4. 只有经验证可复用的衔接流程变化才回写本受管 Skill，并按 CC Switch 的源仓发布流程同步。固定会话换代仍须当前用户单独明确要求并继续遵循本 Skill 的换代协议；普通 Codex 任务交接仍改用 `codex-project-task-handoff`；业务事实处理和业务修复仍遵循所属业务仓规则。

需要路由字段、状态转换和验收口径时，读取 [固定会话路由契约](references/fixed-session-contract.md)。

业务项目需要接入中枢投递、查询路由或确认绑定代次时，读取 [业务消费者接入契约](references/business-consumer-integration-contract.md)；采用固定会话代发时还必须读取 [会话代发契约](references/session-mediated-delivery-contract.md)。

## 创建或绑定一条固定会话

1. 先在公开控制登记表准备一条路由：业务项目、职责、目标业务仓、中枢工作目录、状态和会话策略。公开表只放脱敏别名，绝不写真实会话标识或平台用户标识。
2. 在中枢项目创建对应控制目录，并写清该职责能做什么、必须回到哪个业务仓读取规则、以及与其他职责发生文件冲突时如何停下。
3. 用户明确要求创建或迁移时，在 `cc-connect-operations` 桌面项目中创建或识别一条专用固定会话；标题使用“固定会话｜<业务项目> <职责>”。它是独立上下文，不是业务仓已有聊天的物理搬迁。
4. 先备份私有配置，再使用中枢项目的受控迁移工具，只改已经逐项核对的项目名、工作目录和会话绑定引用。活动绑定必须同时满足“私有映射指向该路由”和“会话实际工作目录等于该控制目录”；`CC_PROJECT` 只校验别名。平台块、允许名单、凭据和既有历史必须原样保留。
5. cc-connect 当前没有离线预建移动会话的命令。没有首次入站消息时，路由应显示为 `awaiting_first_inbound`，不要为测试而自发消息或伪造会话。
6. 首次入站后，确认路由别名、实际工作目录、持久会话策略、通道加载、唯一进程链和预期固定会话都一致。用户明确要求排查角色错配时，补充最小必要会话证据；全部满足后才标记为 `active`。

### 新增绑定会话的一站式接入

用户明确要求新增“业务项目 + 职责”绑定时，按以下顺序完成：

1. 先用中枢 `scripts/scaffold_control_route.py` 预演，再在中枢创建且仅创建 `projects/<business>/<role>/`。每条路由生成 `AGENTS.md`、`SESSION_INITIALIZATION.md`、职责专属 hook 和 `.codex/hooks.json`：通知发布使用 `SESSION_NOTIFICATION_HOOK.md`，开发/授权控制使用 `SESSION_DEVELOPMENT_CONTROL_HOOK.md`；已有目录、路由或 hook 必须先复用，不重复创建。
2. 在公开登记中登记脱敏 `route_key`、业务来源、职责、控制目录和固定 prompt hook；运行会话键、令牌、正文仍只留在私有运行边界。
3. 通过受控桌面项目编辑能力把该控制目录添加到 `cc-connect-operations` 中枢项目，并回读目录清单确认没有重复项。当前产品没有公开的保存项目源目录 API 时，可在用户已授权本次接入的前提下使用可见桌面交互执行“编辑项目 → 添加文件夹 → 保存”，并以界面回读为准；不得修改 Codex 内部数据库、索引或会话文件。若当前没有桌面控制能力，停在“待用户最后点击保存”并明确提示。
4. 完成路由、工作目录、项目身份、exact hook hash、Hook 审核、会话职责和绑定代次核验后，才允许提交通知意图；未完成时保持 `binding_pending`。

不要用会话清理或合并命令处理迁移历史；旧会话应保留为未绑定历史，除非用户明确批准精确清理。

## 移动消息协作

只向已核验的活动路由发送业务需要的消息。多行内容优先从标准输入传入，避免转义错误；消息必须指定目标项目，必要时再指定目标会话，不能依赖“第一个活动会话”的偶然选择。

默认流程是通过 `/timer/add` 将不透明任务注入固定会话；会话以 Luna low 按固定 hook 读取受控引用，只输出最终通知，由 cc-connect 同一 ReplyCtx 自动回发原飞书会话。会话不得调用 `/send`。原生 `POST /send` 仅是用户明确授权的人工直接回退，且同一幂等键不得双发。

`connectivity_probe` 仅验证本机路由、Hook、Timer 和 ReplyCtx 链路，不生成或推断宏观事实；若要通过飞书发送探针，必须有当轮用户明确的外发授权，且最终是否在飞书可见必须由用户确认。

推荐消息结构：

```text
【业务项目｜职责】主题
结论：一句话说明当前结果。
影响：对数据、交付或决策的影响；没有则写“无”。
下一步：已执行或待执行的动作。
需要你决定：无；或给出一个明确选项。
```

- 不发送凭据、会话标识、原始消息正文、账户/订单信息或未经业务仓授权的外部内容。
- 不发送“链路测试”或重复健康提醒。只有用户明确要求实际投递，或业务产出的待发送事项已达到其发送条件时才投递。
- 宏观、行情等业务消息由业务仓完成来源判定、去重、持久化和发送条件判断；中枢只按已核验路由投递并回读投递结果。
- 发送成功不等于业务处理成功；没有可验证回执时只报告 `delivery_unverified`，不得编造已送达。
- 中枢不伪造“不触发 Agent 的桌面静默追加”；当前交互逻辑是把受控 Timer turn 注入固定会话。固定会话收到提示、领取执行权、生成最终文本和飞书送达分别记录独立状态；不得绕过会话代发自动直发。
- 送达结果为未知时不得自动重发，避免平台其实已接收而产生重复消息。

消息模板、投递确认和定时选择规则见 [消息与定时协作](references/message-and-scheduling.md)。

## 定时唤醒的三层选择

| 目标 | 使用方式 | 要点 |
| --- | --- | --- |
| 唤醒某条 Codex 固定会话继续既有上下文 | 桌面端该会话的计划任务 | 先手工验证提示词；桌面应用未运行时不能声称已执行。 |
| 到精确时点执行一条 cc-connect 路由任务 | cc-connect `cron` | 指定路由、会话策略和幂等提示词；同一业务结果只保留一个有效定时器。 |
| 保证移动桥接进程生命周期 | Windows 计划任务/服务 | 与消息内容无关；改动前先核对任务身份，未经授权不得启停或重建。 |

- 需要持续上下文时使用 `reuse`；一次性、相互隔离的任务使用 `new-per-run`。两者都不是“开机自启动”的替代品。
- 先手工验证提示词，再创建定时器；明确运行窗口、超时、静默策略、失败后的重试边界和去重键。
- 不把轮询当作告警源。桥接因关机、未登录或桌面应用未运行而不可用时，记录可解释状态，等待下一次允许的唤醒；除非业务规则或用户明确要求，不额外发送报错或警告。

## 从业务仓迁移到中枢项目

1. 盘点旧会话、旧路由和既有定时器，只记录公开别名与归属。仅在当前用户明确授权职责诊断时，读取完成判断所需的最少当前角色证据；不得批量读取消息历史。
2. 在中枢中创建或识别替代固定会话，并先完成新的路由验证；不要先解绑旧路由。
3. 备份私有配置，精确更新绑定，并回读结构化健康结果。任何字段无法唯一定位、平台块出现变化或验证失败时立即恢复并停止。
4. 新路由健康后，才把已有桌面计划任务或 cc-connect 定时器改指向新固定会话；同一时刻只能保留一个会触发同一业务结果的定时器。
5. 旧会话保留历史但不再接收新工作。报告迁移完成、旧路由状态、定时器去重结果和仍需用户决定的事项。

### 根目录旧会话

历史上以中枢根目录启动的旧会话不能仅凭 `CC_PROJECT` 认定为某条活动路由。继续使用前必须由用户显式指定项目与职责，并核验其实际工作目录；根目录旧会话只保留历史或用于一次性人工初始化，不承接自动投递。需要持续使用时，为相应控制目录创建后继候选会话，按换代协议验证后再激活；不自动改绑、删除或把根会话冒充为控制目录会话。

## 桌面发起的 cc-connect 固定会话换代

只在当前用户明确要求“为指定 cc-connect 路由创建后继固定会话并重绑”时执行。普通开发任务因上下文长度而接力不进入本节。不得按上下文长度、空闲时长、定时器或失败重试自动换代。

1. 先读取 [会话换代与双向验证协议](references/session-rollover-protocol.md)，并核对路由职责、业务确认状态和中枢健康状态；任何一项不明确时停止。
2. 仅使用中枢提供的受控 Bridge 适配层创建候选代次。Bridge 在这里仅服务会话换代，不是主动飞书文本出口。候选创建后，中枢运行账本保持为 `binding_pending`；静态公开路由登记不写入代次或会话状态。旧代次保留为历史，绝不删除、合并或用新代次覆盖。
3. 提示用户在原移动聊天发送一条普通“激活新会话”消息；不要建议发送 `/new` 或其他会额外创建会话的指令。
4. 按“候选职责匹配 → 移动入站与桌面会话关联 → 新会话产生可验证响应 → 业务项目确认绑定代次”的顺序回读。只有全部通过后，才标记新代次 `active` 并恢复该路由的自动投递。
5. 验证失败时保留旧代次和候选记录，将自动投递停留为待发送或可重试状态；只允许用户明确取消或回退。桌面侧栏未刷新时，仅提示用户自行刷新桌面端，不强制结束应用。

## 健康判断与报告

默认使用中枢项目的健康脚本、任务状态和唯一进程链回读。当前用户明确要求核对会话职责、显示名称或路由串线时，可按“最小必要职责核验”通过官方接口读取实际工作目录、路由归属、Hook 和最少相关会话证据；不要只凭显示名称判断。无论是否授权诊断，都不得直接读写 Codex 数据库、索引或会话文件，也不得输出或持久化凭据、令牌、会话键、完整私有配置或会话原文。

- `active`：路由、工作目录、持久策略、通道和进程链均匹配。
- `awaiting_first_inbound`：公开路由已准备，但尚未由真实入站创建会话。
- `binding_mismatch`：公开登记、私有绑定或固定会话归属不一致；停止迁移与发送。
- `bridge_not_running`：桥接未运行；不擅自重启，除非当前用户已授权该任务操作。
- `desktop_app_unavailable`：桌面固定会话计划任务不能执行；不伪报完成。
- `delivery_unverified`：没有可验证回执；不得称“已送达”。
- `session_prompt_accepted`：Timer 已被 cc-connect 接受，但不等于会话已执行或飞书已发送。
- `session_prompt_unverified`：Timer POST 结果未知；同一幂等键不得再次创建 Timer。
- `session_publish_unverified`：固定会话已解析内容并领取一次性发布权、即将输出最终文本；只说明发布尝试已生成，飞书送达和已读仍未知。
- `registration_unknown`：投递意图 POST 可能已被中枢登记但业务侧未获得可信响应；只做认证对账，不再次 POST。
- `suppressed_unknown`：历史或当前登记状态无法安全证明“从未登记”；不计入可重试待发送或送达未验证，同一幂等键永久抑制自动重发。
- `bridge_incompatible`：Bridge 协议探测或兼容性检查失败；只停止依赖 Bridge 的会话换代或绑定变更，不改写会话或私有配置。它不代表已独立验证的原生 UDS 飞书主动文本出口不可用。
- `consumer_unacknowledged`：中枢已存在候选绑定代次但业务项目尚未确认；保留待发送项，不向新代次投递。
- `desktop_not_supported`：只表示不支持“不触发 Agent 的纯静默追加”；不得据此绕过默认的固定会话代发流程。

最终用自然中文说明：路由、会话、通道、定时器分别是否就绪；本次有没有实际发送或改动；以及用户是否还需要作出一个具体决定。不要输出私有路径、原始配置、完整会话标识或消息正文。
