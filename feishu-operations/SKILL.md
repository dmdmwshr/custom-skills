# 飞书操作

先确定本次要改变或核验的飞书对象与结果，再选择下面的流程。以当前应用能力、官方接口或可见后台为准，不把旧版本界面、权限名或历史回执当作当前事实。

## 选择职责与入口

| 请求 | 本 Skill 的职责 | 按需读取 |
| --- | --- | --- |
| 应用/机器人名称、描述、权限、事件、可用范围、发布 | 核对唯一应用，实施最小变更，回读发布生效状态 | [应用维护与发布](references/app-maintenance.md) |
| 消息未收到、乱码、发送错误、入站丢失、回复不可见 | 分层定位平台接收、事件、传输和用户可见性 | [消息排障与验收](references/messaging.md) |
| cc-connect 路由、任务 cwd、Hook 或绑定错误 | 把证据交给 cc-connect-collaboration；不在这里重绑 | 读取该 Skill，平台部分仍由本 Skill 处理 |
| 新增飞书能力、总结经验、优化本 Skill | 先决定归属再修改，检查原流程回归 | [持续优化规范](references/maintenance.md) |

1. 核对实际目标主机、已安装能力及当前用户身份。优先使用能力匹配的受控连接器、官方 API 或现有 CLI；不为本次排障新建第二发送器或后台服务。
2. 没有合适接口且确需页面操作时，遵循当前环境的浏览器授权要求；复用已登录的目标环境，不读取 Cookie、浏览器存储或认证令牌。不能操作时报告缺少的入口，不伪称已完成。
3. 只读诊断不授权发布、发消息或改权限。用户已经明确指定对象、目标和动作时，直接执行范围内步骤；仅在应用无法唯一识别、最终字段缺失或平台要求扩大权限/范围时询问，不对已批准动作反复确认。
4. 身份关联在受控接口或内存中核对。App Secret、token、Cookie、私有聊天/用户标识不进入 Skill、Git、公开台账或回复。需要认证时使用既有受管凭据入口，不打印密钥或完整请求/响应。
5. 接口超时或执行结果未知时，先按原对象/请求的只读回执对账，不盲重试保存、发布或发送。每次验证使用独立回执位置，记录阶段与真实结果，保留旧失败证据。

## 与业务及中枢的边界

本 Skill 管飞书平台，不生成宏观/交易事实，不解释业务授权，不维护 Codex 数据库或自动化目标。跨层任务只交换必要的脱敏对象别名、预期职责、配置差异和状态证据。

cc-connect 已管理的消息必须走其既有受控出口；平台诊断不能绕过路由代次、允许名单、投递意图或唯一写入者。直接通知和移动入站固定任务分别核验：其中一条失败不代表另一条失败。路由为桌面专属出站模式时，入站静默丢弃属于预期行为，不开启双向收信作为修复。

## 完成口径

分别报告：配置是否保存、版本是否已发布并生效、平台是否接受请求、目标是否可见、业务/固定任务是否完成。缺哪一项就明确保留未知；发布成功不等于送达，任务产出回复不等于用户已看到。只有确实需要用户在原聊天发普通消息或确认可见性时才安排人工步骤，不建议 `/new` 或重建任务。

新问题先落对应项目的现有台账；只有用户要求沉淀且已验证可复用时，才按持续优化规范修改源仓。发现一次新错误不自动扩展 Skill 或新增常驻监控。
