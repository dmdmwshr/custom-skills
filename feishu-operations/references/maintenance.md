# 持续优化规范

本规范约束后续飞书功能的扩展与经验沉淀，不授权自动修改 Skill、平台或启动常驻整理任务。

## 内容归属

- SKILL.md 只放触发范围、分流、最小公共流程、权限边界和完成口径，目标不超过 150 行；接近上限先合并或拆分，不能直接追加事故记录。
- app-maintenance.md 唯一维护应用配置与发布流程；messaging.md 唯一维护收发分层和验收。
- 新增独立飞书能力时，先证明不能自然归入现有参考，再建一个主题参考文件，并在主说明增加入口。参考最多一层跳转；禁止出现 A→B→A 的必读循环。
- 中枢路由/Hook/绑定/账本归 cc-connect-collaboration，业务语义归业务 Skill，主机工具安装归本机说明。这里只保留职责交接口，不复制另一份规则。
- 固定应用 ID、聊天标识、凭据、临时错误、任务 ID、当天进度和原始回执不进入 Skill；放在所属项目的现有私有证据/脱敏台账中。不要新增第二个计划或反馈入口。

## 每次优化的步骤

1. 先写清触发案例、已验证根因、适用边界和期望行为；未经验证的猜测只记待查问题。区分平台机制变化与单机偶发故障。
2. 搜索现有触发词和规则，选择“替换过时规则、合并重复内容、补充现有流程、确需新主题”之一。新需求优先于旧规则；矛盾必须在原规则处消除，不在文末追加反向例外。
3. 每条新增规则说明放在哪一层以及为何；记录在本次提交说明/项目验收材料，不给 Skill 堆变更日记。引用当前官方依据时只保留必要稳定入口和适用条件，运行时仍核验实际能力。
4. 在 custom-skills 源仓编辑，只提交本次精确文件；校验 frontmatter、相对链接、入口可达、引用无循环、重复/冲突和以下场景。不要直接改受管安装副本。
5. 按本机受管流程完成验证、提交推送、安装、哈希比对和新进程唯一发现。新 Skill 同步登记受管平台清单；只安装授权主机，不把 WSL 验证宣称为 Windows 或飞书业务实测。

## 每次修改都要检查的场景

| 场景 | 预期行为 |
| --- | --- |
| 仅改应用名，绑定正确 | 应用维护；保留身份/权限/绑定 |
| 保存成功但待审核 | 报告未发布，不称完成 |
| 既有草稿包含他人权限变更 | 隔离本次改动，不能打包发布 |
| 同名应用无法唯一识别 | 停止写入并澄清对象 |
| 发送超时且可能已接受 | 原请求只读对账，不重复发送 |
| cc 任务 cwd/Hook 错 | 转交中枢，不在飞书侧换绑 |
| 出站专属路由丢弃入站 | 视为预期边界，不开启双向链 |
| 原 owner 获专项授权只读查看飞书 | 核验唯一目标与可见性，不反推机器回执/本人已读，不补发 |
| 用户要求新增飞书文档/表格等能力 | 先设计独立主题及最小权限，再实现；现有消息规则不冒充该能力 |
| 新经验与旧规则重复或冲突 | 在唯一归属处合并/替换，并复查上述场景 |

静态检查和场景走查只证明说明结构与决策一致性，不证明飞书实际发布/发送成功。真实平台变更仍按具体用户需求执行，绝不为了发布 Skill 触发外发验收。
