# 消息排障与验收

## 先分层，后验证

| 现象/证据 | 首先核验 | 不应采取的动作 |
| --- | --- | --- |
| 应用名错，路由职责正确 | 应用展示信息与发布生效版本 | 交换绑定、重建任务 |
| 自动通知不可见 | 原投递意图/发送回执，再查平台错误与目标范围 | 重新生成同一意图或另走 API 补发 |
| 用户消息未进入任务 | 订阅/接收方式、权限与范围，再交中枢查路由模式 | 默认开启被设计为静默丢弃的入站 |
| 任务已回复但飞书未显示 | 回发传输与平台独立回执、用户可见性 | 把任务完成等同送达 |
| 中文乱码 | 正文生成、传输编码与平台呈现的边界 | 用真实群发试错、只用 ASCII 自检 |

1. 用最少的脱敏请求/事件关联和阶段结果定位；先查现有回执，禁止批量读聊天历史。对 cc-connect 管理路由，投递幂等性、未知状态和消费账本以中枢契约为准。
2. 只有确认问题在飞书层，才核对实际应用的机器人能力、必要权限、可用范围、发布状态及事件接收方式。使用当前官方字段与错误语义，鉴权错误不能通过扩大权限或更换应用试错。
3. 乱码先在本机做不外发的中文逐字节往返测试，再检查实际传输边界。平台 Skill 不复制操作系统适配器代码；cc-connect 的 Windows/WSL 编码实现交给中枢已有流程。
4. 无外发检查通过后，若已有明确发送授权，选择一个唯一目标和最小、非业务验证内容，通过原受控出口发送一次。记录原请求的阶段与结果；未知结果按可能已接受处理，只读对账，不自动重发或换目标补试。

## 真实收发验收

1. 先确认路由/平台已准备好，再请用户在指定原聊天发普通验证消息；多职责用不同短序号，逐个验证，不发送 `/new`。
2. 入站到固定任务的身份、完整 cwd、Hook、回合完成及是否创建重复任务由 cc-connect-collaboration 通过官方接口检查。只看完成判断必要的最近回合，不复制正文。
3. 独立记录平台接受结果。用户确认原聊天可见回复可作为可见性证据；若当前用户有专项授权且原任务拥有对应浏览器能力，也可由原任务只读核验唯一原目标、时间与最小必要内容，不以预先取得 transport_accepted 为页面观察前提。网页可见不能反推机器送达回执，也不等于用户本人已读。没有任一可见性证据时明确“回发可见性待验收”；不因此补发。普通探针仍遵循原路由的用户确认门禁，专项例外不能扩大其他路由的发送或浏览器权限。
4. 如原路由仅允许出站，不要求入站回复作为验收，也不启动其他任务验证。最终只报告已覆盖的方向。

回执只保存对象别名、方向、阶段、错误类别、退出码（适用时）、日志哈希、UTC时间和可见性结论。保留失败与未知记录；测试消息不包含凭据、账户、交易授权或业务动作。
