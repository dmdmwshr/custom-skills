# 官方飞书 CLI

## 选择与认证

- 官方来源为 [larksuite/cli](https://github.com/larksuite/cli)，npm包 `@larksuite/cli`，命令 `lark-cli`。先查实际 `--version`、所需命令 `--help`；安装、升级和公共路径按目标主机受管工具链执行，不用安装成功代替账号认证或业务验收。
- 复用原应用；显式选择 `--as bot` 或 `--as user`。bot 查询不能证明收件用户可访问；user 查询必须核实登录用户。既有 cc-connect 消息继续走原出口，不调用 CLI 发送补验，不新建应用、监听器或第二投递链。
- `auth status --json` 是本地状态，`--verify` 才请求服务器；回传前提取所需布尔/错误类别，不整段公开身份或令牌。先用 `config init --help`、`auth login --help` 核实当前配置/认证参数，凭据仅经原受管入口或标准输入，不放命令行参数、Git、Skill或普通日志。
- 默认申请当前动作所需权限；用户明确要求全业务域/最大 CLI 权限时，可按当前帮助使用 `auth login --domain all`，不得仍按旧最小集合完成后声称全域。分别记录请求域、实际获批 scope、身份和实际调用结果；all 是 CLI 当前支持域的用户授权，不是飞书租户超级管理员，也不自动增加 bot 权限或资源访问权。认证失败不换应用或扩大权限试错。
- 具体文档、日历、任务、邮箱等动作先读取当前版本内置 `lark-cli skills read <对应技能>` 和其必读参考，再查命令帮助；不把消息能力或本机旧示例当作其他业务域已验收。

## 需要用户协助的分步授权

1. 在本任务私有0700目录执行 `auth login ... --no-wait --json`，umask077。临时响应、device code、二维码仅保存在该目录的0600文件，不进入Git、普通日志或Skill。按当前内置认证说明展示原样授权链接及二维码，明确有效期；CLI输出路径用工作目录内相对路径。
2. 用户确认后，用该次原始device code按当前帮助续接一次；不重新发起另一个登录。过期或已消费不能复用；执行结果未知先回读已有凭证和回执，不盲目重复轮询。等待用户期间继续不依赖认证的工作。
3. 先保存实际进程结果，再做脱敏摘要，区分平台执行、调用方解析和后续检查。分别捕获stdout/stderr；错误流可能混有进度提示，不能因整段不是JSON就推定平台未执行。若退出非零但服务器 `auth status --verify --json` 已证实用户有效、扩展scope已保存，分别记录两事实，不重复授权；未保留原错误时不得臆断根因。
4. 按实际命令的输出结构解释结果：普通API信封检查 `ok`、退出码和逐项结果；认证状态按其 `verified`、身份状态及scope字段，不要求它具有普通API的 `ok`。scope可能包含此前累积授权，不能把本次请求集合当作最终集合。
5. 确认无在途且授权已消费/过期后，精确清理本次临时认证响应和二维码，留下无凭据回执。保留CLI自己的受管凭据存储，不删除账号配置，也不输出token验证登录。

## 有界能力测试与迁移判定

- 用户身份、bot身份、应用已发布权限、资源所有者/管理员角色分别验证。同一命令user成功、bot缺scope是两项结果；用户重新OAuth不会修复bot缺权限。依据当前错误提示在原应用单独配置/发布必要权限，不能顺便把所有bot权限勾满。
- 优先选已授权对象的单页只读调用，报告身份、UTC、退出码、结构化状态、条数/错误码，不输出正文和私有ID。空成功证明请求可调用，不证明拥有资源或读写全部功能；不同域分别留证。
- 写能力默认先用支持的 `--dry-run` 验证请求构造。明确写成“未执行/未证明服务端写权限”；测试授权不等于可任意发消息、删数据、发布应用或创建机器人。真实写验收需具体对象和预期结果。
- 邮箱、文档等即使scope存在仍可能因产品开通、资源范围或参数失败；记录实际错误，查当前官方依据后定位，不猜测失败原因、不为测试开通收费功能。

## 原消息的只读核验

以下命令形态已在1.0.96实际帮助中核对；平台调用仍须独立验收。仅查询本次授权的消息，不批量扫聊天寻找替代目标。原ID仅有哈希时，可按已批准的原关键词、发送者类型和精确时间窗单页搜索；内存中与原ID/目标哈希唯一匹配后才继续，不把相似新消息当作原通知。

- `im +messages-mget --as bot|user --message-ids <原ID> --no-reactions --format json`：取原消息。默认不下载资源，不加 `--download-resources`；正文只在私有处理边界比对。富文本渲染内容与原始JSON不是同一种哈希输入。
- `im +messages-read-status --as user --message-ids <原ID> --format json`：当前用户已读状态。`invalid_message_ids` 不能直接解释为消息没发送或没读。
- `im +message-read-users --as bot|user --message-id <原ID> --format json`：受发送者身份和七天时限约束，运行时复核官方API要求；查询原bot发送消息不能换一个新bot。默认单页，需要分页时限定页数，不无界拉取。
- 按实际命令的结构化成功字段解释输出，不对所有 CLI 结果套用 OpenAPI 的顶层 `code=0`；退出0、响应合法、目标精确匹配分别核对。超时或结果未知先查已有回执，不重发。
- `im +messages-search` 会自动补取正文与聊天上下文；敏感内容只在私有处理边界内存中核对。`--page-size` 限单页，显式 `--page-limit` 会开启自动翻页，不能把它当普通单页限制；只读精确核验不加 `--page-all`，也不下载附件。

分别记录平台消息存在、原目标/发送者匹配、用户身份可访问、平台报告已读、网页实际可见及用户本人确认。任何一项不能代替其他项；原任务仍要求网页观察时，用获准的自有页面只读完成，用户明确允许显示浏览器的专项例外按原范围执行，不通过页面发送。

## 兜底与完成

命令不存在/能力缺失→既有受控API；缺权限/认证→具体说明缺口，不能绕过权限；确需可见界面证据→按原owner与隐藏资料约束访问网页。CLI调用不自动授予读取其他消息、改权限、发布版本或外发权限。

私有临时结果仅按本次任务允许的目录/权限和保留期限管理，结束后核对无在途再精确清理；回执只保留对象别名、UTC、阶段、结果/错误类别和必要哈希，不存正文、token或用户私有标识。
