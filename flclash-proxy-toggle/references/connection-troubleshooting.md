# FlClash 连接与流量排故

## 适用范围与边界

用于排查浏览器开启代理后无法联网、`ERR_PROXY_CONNECTION_FAILED`、节点延迟正常但实际访问超时、某一协议失败、CN2/Meifu 无流量、或仅在 TUN 启用后异常的情形。

先做本机只读判断，再决定是否需要服务器日志。排故不授权暂停、退出、重启 FlClash，不授权关闭连接、刷新订阅、切换节点、修改系统代理、TUN、Windows 路由或服务器配置。任何修复动作都必须取得用户对该精确动作的单独授权。

不要把订阅中节点条目多、单次延迟面板超时或某个 UDP 节点失败直接解释为“服务器堵塞”。这些都不是充分证据。

## 固定采集顺序

1. 先运行：

   ```powershell
   <可信 Python 解释器> scripts/flclash_state.py --connectivity
   ```

   该诊断只读取：Windows 系统代理是否指向回环地址、该端口是否与生成的混合端口一致、FlClashCore 是否实际监听、回环 controller 的分流选择，以及活跃连接的已汇总归属。它不发起外网测速，不输出 controller 密钥、订阅链接、节点服务器或访问目标。

2. 仅当本机混合端口和运行时分流都已证实正常，才请求用户提供精确的失败时间，并和服务器的脱敏握手日志对照。

3. 若问题只在 TUN 启用时出现，先只读查看默认路由和已连接网卡；实际能上网的接口必须承载优先级最高的默认路由。没有明确授权，不得修改接口跃点数或路由。

## 诊断结果的中文含义

| 诊断标记 | 中文含义与结论 |
|---|---|
| `local_proxy_not_listening` | Windows 已把浏览器导向本机代理，但生成的混合端口没有监听；请求还没到服务器，先查 FlClash 核心启动和端口状态。 |
| `system_proxy_port_mismatch` | Windows 系统代理的本地端口与生成配置的混合端口不一致；浏览器可能被送往旧端口。 |
| `local_port_owned_by_other_process` | 端口可连但监听者不是 FlClashCore；不能直接结束该进程，先确认占用归属和用户授权。 |
| `local_proxy_listener_unreachable` | 虽检测到 FlClashCore 的监听记录，但 Windows 回环地址无法连通该端口；先查绑定范围或核心运行态，不能视为入口正常。 |
| `local_proxy_listener_ready` | FlClashCore 正在监听匹配的本机端口；只说明本机入口已通过，不能单独证明远端出口一定可用。 |
| `cn2_idle_by_current_selection` | 当前上层代理出口未选 CN2，且快照中没有 CN2 连接；CN2 无流量属于当前分流结果，不能据此判定 CN2 故障。 |

诊断中 `controller_runtime` 只统计连接归属。它是当时的快照；没有活跃请求时，不能用“零连接”断言某节点不可用。

## 证据到结论的分流表

| 现象和证据 | 可下的结论 | 下一步边界 |
|---|---|---|
| 浏览器报本机代理连接失败，且本机混合端口未监听 | 本机 FlClash 核心/端口链路故障；远端服务器通常还未收到请求 | 保持网络现状；说明端口和核心证据。若要恢复核心或端口，先取得明确授权。 |
| 本机端口已由 FlClashCore 监听，但 Windows 系统代理端口不匹配 | 本机系统代理配置不一致 | 不擅自关闭系统代理或改端口；提出精确修复项并等待授权。 |
| 本机端口和分流正常，实际请求在服务器没有对应握手记录 | 本机出口、办公网络、DNS、网关或安全设备仍可能拦截；尚不能称为服务器故障 | 收集准确时间和协议，再做最小范围的本地/服务端只读比对。 |
| WS 或 gRPC 有正常握手和短请求，Hysteria2 单独反复断开 | 高度怀疑办公网络、NAT 或安全设备限制 UDP/QUIC；这不是“节点太多”证据 | 经用户同意后优先选择现有 WS/gRPC 兼容节点；不要自行删改 Hysteria2。 |
| 同一时间 WS/gRPC、Reality 都被服务端拒绝、认证失败或后端异常 | 服务器协议、证书、转发或后端故障有直接证据 | 只在用户授权后针对命中的服务做最小修复。 |
| 服务端有 WS `101` 或 gRPC `200`，随后客户端主动关闭或测速到固定上限 | 握手已到服务器；测速面板可能在本地超时或主动取消，不能据此认定服务器拥塞 | 用真实、短时的公开网页访问验证；不要以批量延迟面板为唯一证据。 |
| CN2 组内已选节点，但代理出口、OpenAI 或 OKX 上层组选择 Meifu | CN2 节点“被选中”只代表组内预选，不代表业务流量会经过 CN2 | 先报告分流层级；只有用户明确要求时才切换上层组。 |
| 仅启用 TUN 后全部节点异常 | 默认路由优先级或虚拟网卡接管可能异常 | 先查默认路由和网卡优先级；不凭经验修改接口跃点数。 |

## CN2 与 Meifu 的流量判断

判断实际流量必须按“上层分流组 → 对应服务组 → 具体节点”的顺序：

1. `代理出口`、`OpenAI`、`OKX` 等上层组决定业务交给 CN2、Meifu、链式代理还是直连。
2. 被选中的服务组再决定使用该组内的哪一个节点。
3. controller 活跃连接归属才是当前业务路径的快照。

因此，CN2 组中有一个当前节点、但上层仍选择 Meifu 时，CN2 没有流量是预期结果，而不是线路失效。反过来，零活跃连接也只能说明当时无业务经过，不能证明节点不可用。

## 服务器日志对照规范

仅在本机入口已通过后进行。要求用户提供北京时间的短时间范围和实际失败的协议/节点类别；服务器侧只读取对应时间窗的脱敏访问、四层握手和 Hysteria2 状态日志。

记录来源公网地址、协议类别、HTTP/握手结果、持续时间和聚合字节数即可。不得记录订阅认证字段、访问正文、完整目标地址或可复用凭据。没有能按时间对应的完整证据链时，结论写“证据不足”，不要把猜测写成服务器故障。
