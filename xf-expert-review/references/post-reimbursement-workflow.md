# 报销后整理与待发邮箱

适用于用户要求将指定评审报销后迁移、整理待发邮箱或补齐收尾。目录命名和索引同步属于获授权迁移的必要步骤；实际付款、报销提交、发邮件不由迁移授权推导。仅审查、盘点或优化 Skill 时只读业务资料。

## 先核对当前事实

1. 按 [本机资料入口](local-sources.md) 读取项目规则、实时总表、资料索引、排除事项、人工确认及最近快照。固定评审编号、项目、阶段和实际劳务名单；同项目不同年度、需求／技术／初验／终验不得凭简称合并。
2. 用户本次明确“已报销”可以支持报销状态更新；材料存在、脚本成功不能代替报销完成证据。对比最新手改，保留人工值并记明冲突，历史确认不强行覆盖新手改。
3. 盘点本次原目录、待发邮箱、具体项目阶段归档目标；排除锁文件和维护产物。记录文件相对路径、大小、内容校验值，以及目录原名、必要备注和本次目标名。原目录名中的经办科室、暂缺扫描件、联合评审、特殊办理情况均须保留。

## 待发邮箱目录命名

默认形如：`项目序号.该项目评审序号、完整项目名称-评审阶段（劳务专家甲、劳务专家乙）（原有必要备注）`。

- **序号沿用同项目分组。** 扫描待发邮箱直接子目录，连同已发送项一起核对。现有 `0.1.3、…（已发送）` 中的项目号为 1、评审序号为 3；新迁入同项目下一次评审应接 1.4，不能忽略已发送项后重用 1.3。`0.` 是既有排序前缀，迁入待发送不能自行添加；也不因此改动历史目录。
- **不按评审阶段写死数字。** 已有同次评审复用原序号；新阶段按该项目已用最大序号加一。新项目用已用最大项目号加一，不填历史缺号、不重排已有项目。同名不同年度、别名和归档项目编号不自动等同；先以索引和材料核实对应关系。
- **括号列实际劳务专家。** 从本次已核实劳务表取姓名，按表内顺序、去除普通／全角空格后去重，以顿号连接；不从证书数量或签到人数推断，不加基层代表、参建人员。缺可靠名单时标明缺口，不生成貌似完整的姓名括号。
- **备注与专家括号分别保留。** 原有“某科室自行开展、暂时没有扫描件”等原文独立放在专家括号后，不能被规范命名覆盖。项目正文内的“（二期）”等属于项目名，不能当备注删掉。资料补齐后如需改备注，须有新证据；改前文字留在维护记录中。
- **发送标记按事实。** 已有“已发送”保留；只迁移不增加该标记。已发送状态冲突以实时人工确认规则处理，不凭目录排序号判断发送成功。
- **重复执行先认同次。** 根据稳定评审编号和当前索引检查已经迁移的目录；已有目标则核对差异，不再分配新号、再复制一套或覆盖不同内容。

### 命名辅助工具

`scripts/plan_mail_directory.py` 只读待发邮箱直接子目录并输出名称计划，无移动、复制或写台账功能。先核实同项目目录清单；工具不根据模糊项目名猜分组。

选择文件放本次维护执行目录，不放 Skill 仓库。字段如下：

```json
{
  "review_id": "PS-示例",
  "project_name": "某信息化采购项目",
  "stage": "初验",
  "experts": ["专家甲", "专家乙"],
  "project_members": ["1.1、该项目已有阶段（专家甲）", "0.1.2、该项目另一阶段（专家乙）（已发送）"],
  "source_name": "该项目初验（某科室开展，暂缺扫描件）",
  "current_name": null,
  "remarks": []
}
```

`project_members` 填已经核实属于本项目的现存目录原名；新项目用空列表。`current_name` 仅在同次评审已经位于待发邮箱时填写其当前原名，用于复用序号和原位更名。工具保留 `source_name` 及 `current_name` 尾部非专家、非发送状态括号原文，`remarks` 只补充必要备注；输出后仍须核对是否有正文里的备注需要补入。不可把身份证、银行账户等填进选择文件。

运行：`python scripts/plan_mail_directory.py --mail-root <待发邮箱目录> --selection <本次选择.json>`。出现缺失成员、分组冲突、重号、非法名称或目标碰撞时仅返回问题，先核实，不强制覆盖。

## 文件、归档与台账一起收尾

1. **制定具体路径映射。** 最终邮件目录名一次确定，列出原目录→邮件目录→项目年度／阶段归档目录。归档名称沿用该项目档案习惯，不照搬待发邮箱序号。解析绝对路径并核对边界，确认目标无不同内容冲突。
2. **保留报销后完整来源。** 邮件资料删减前建立当前来源清单；缺签字意见、劳务或签到扫描件等材料时，记录“现有材料清单”和具体缺口，不能称为完整版本基准。复制现有资料可完成局部归档，但不能据两处文件相同升级为“已归档”。
3. **按已授权范围执行。** 迁移及归档复制前核对源哈希没有变化；已有同名同内容只核验复用，有不同内容保留版本差异。目录调整后逐项核对相对路径、数量、大小与哈希；记录原路径是否仍存在。失败保留已完成步骤和原断点，先回读再续做。
4. **写回唯一总表和索引。** 用当前表头定位所需单元格，先备份，保存前再次核对文件哈希并取得独占访问。报销、邮件和归档分别更新；缺件保留部分归档／待核实。搬移不删除评审记录、不改变已核实专家次数。只把必要说明留总表，资料位置更新 `评审资料索引.json` 及同名 Markdown，不恢复已删四列或另建隐藏表。目录更名时一起更新对应劳务依据、工作资料、邮件位置及当前版本来源；历史回执原路径保持原样。
5. **回读与快照。** 原生重算、保存重开，核对受影响状态、待办、专家／年度次数、手改保护及所有更新后的路径。新增人工确认逐字段追加历史。只接受本次确已审阅的来源变化，不用整盘扫描结果覆盖未核实的新变化。总表被占用时可保留候选和已执行步骤，不能宣称台账已经同步。
6. **清楚交付。** 报告迁移及命名结果、文件核对、台账同步情况和具体缺件；发送与归档都完成才报办结。仅当有新证据时重复提醒已有缺件。若同场汇总与总台账的次数口径不一致，单独记录待对齐项，不把“旧合计不变”写成整项验收结论。

验收至少覆盖：目标序号无重复、劳务专家括号正确、原备注保留、同次重跑不新建、文件内容一致、索引均可达、三个状态各有依据、人工修改及历史事实保留。无需为一次命名整理重做不受影响的全部历史验收。
