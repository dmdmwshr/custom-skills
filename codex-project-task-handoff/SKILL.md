# 普通项目任务接力

把用户口中的“换新会话”理解为新建一个普通 Codex 项目任务。每个项目只维护一份可变的当前交接快照；每次接力先更新这份文档，再让后继任务从文档和当前工作区恢复上下文。不要复制旧任务的完整历史，也不要为每次接力新增一份交接文件。

## 先判定接力对象

- 当前普通开发任务因为轮次多、上下文长，需要在同一项目继续查看、优化或下达新任务：使用本 Skill。
- 请求涉及 cc-connect、固定会话、移动端、飞书、微信、控制路由、`work_dir`、绑定代次或重新激活：停止本流程，改用 `cc-connect-collaboration`。
- “换会话”没有任何项目或路由线索且两者仍可能成立时，只问一个简短问题；未判明前不创建、改名或归档。

本 Skill 不读取或修改 cc-connect 的私有映射、路由账本、Bridge、ReplyCtx 或通道配置。

## 授权与不变量

- 只有用户在当前消息明确要求任务接力时才执行。不得仅因估算上下文长度、轮次、空闲时间或定时器自动触发。
- 一次明确的项目任务接力授权，覆盖读取当前项目状态、创建或更新项目内唯一交接文档、创建并初始化后继任务，以及成功后的改名和归档。这不授权提交、推送、部署、启停服务、删除旧交接文件或其他项目变更。
- 唯一交接文档无法安全确定、无法写入或无法被后继任务读取时，停止在创建后继任务之前并报告阻塞；不能退回只写聊天提示的旧方式。
- 新任务未取得真实 `threadId`、未完成初始化或无法回读时，旧任务保持原名且不归档。
- 不删除旧任务，不改写其历史，不手工编辑 Codex 数据库、索引或会话文件。
- 不使用 `fork_thread`：它会复制已完成历史，无法达到缩短上下文的目的。
- 不使用 `handoff_thread`：它用于移动既有任务及 Git 状态，不用于创建精简上下文的后继任务。

## 确定项目内唯一交接文档

先读取 [唯一交接文档与启动包模板](references/handoff-package.md)，再按以下顺序确定文件：

1. 读取适用的项目规则；如果规则已声明唯一交接文档，必须使用其精确路径。
2. 未声明时，默认使用项目根目录的 `PROJECT_HANDOFF.md`。若项目已有一份明确承担跨任务交接职责的文档，可继续沿用，但不得同时创建默认文件。
3. 在项目根目录及项目规则指定的文档目录中，按文件名和文件标题检查 `HANDOFF`、`SESSION_NOTES`、`CONTEXT`、`交接` 等用途相近的活动文档。发现两份及以上无法区分的活动交接文档时停止，不擅自删除、覆盖或合并。
4. 时间戳副本、旧任务专属交接文件和新建的等价计划文件均不允许。历史归档若项目本来就有，只可只读保留，不能被当作当前交接入口。
5. 交接文档是“当前事实快照”，不是路线图、待办库或第二份项目计划；项目已有唯一计划时，只引用它，不复制或改写其职责。

Git 项目默认保留交接文档为普通工作树改动，不自动暂存或提交。非 Git 项目也在项目根目录或规则指定位置维护同一份文档。只有当前主协调任务更新该文档。

## 更新并核验交接文档

创建后继任务前，先以 UTF-8 原地更新唯一交接文档，并只在当前项目范围内重新核验：

1. 项目名称、目录、目标和当前阶段。
2. 项目级与全局 `AGENTS.md`、唯一计划、README 和架构说明。
3. 当前 Git 分支、工作区改动、最近相关提交；不得重置、清理或擅自提交。
4. 已完成事项、验证证据、仍在运行的进程或后台任务。
5. 未完成事项、阻塞、已否决方案、风险边界和建议下一步。
6. 用户随接力请求明确下达的首项新任务；没有则写“仅初始化，等待用户下达任务”。

文档至少包含：更新时间与时区、项目身份、当前有效规则、已完成事项及证据等级、Git/工作区状态、服务和后台任务、未完成与阻塞、禁止动作、后继任务首项工作。区分“当前回读确认”“旧任务中的历史结论”和“尚待验证”，不得把计划写成已完成。

易变化事实必须在本轮重新读取；无法安全核验时写明“尚待验证”，不能沿用旧结论冒充当前状态。不把敏感信息、完整终端输出、长对话、内部会话标识、凭据或无关文件写入文档。复杂项目优先引用项目内事实源，避免让交接文档无限增长。

更新后必须回读并确认：

- 项目当前只有一个明确的活动交接入口。
- 文档路径、更新时间、分支或版本、工作区改动、未完成事项和首项任务彼此一致。
- 没有新增等价计划、时间戳交接副本或敏感内容。
- Git 项目对该文件的差异可正常解析；不得为通过核验而清理用户改动。

任一项不满足时不创建后继任务。

## 创建并初始化后继任务

1. 先查询 Codex 已保存项目，优先复用当前任务的项目绑定；未绑定时，只在当前目录能唯一匹配一个保存项目时使用该项目。无法唯一定位则停止并请用户指定。
2. 创建普通项目任务，不创建 cc-connect 固定会话，标题使用 `<项目>｜<当前阶段或首项任务>`。
3. Git 项目默认使用独立 worktree，并从当前 working tree 创建，确保唯一交接文档和用户尚未提交的工作能随项目状态进入后继任务。用户明确指定分支或提交时，必须先确认该起点已经包含可读取的唯一交接文档，否则停止。非 Git 项目使用保存项目的本地目录。除非用户明确指定，否则不覆盖模型和思考强度。
4. 初始提示只携带精简启动包：唯一交接文档的项目内路径、项目身份、事实更新时间、首项任务和必要边界。要求新任务先完整读取适用规则、唯一交接文档、唯一计划、README/架构说明和当前 Git 状态，再核对易变化事实；不要把整份交接文档或旧聊天重复粘贴进提示。
5. 用户没有附带首项任务时，新任务只做只读初始化并回报准备状态，不修改文件或运行态；用户附带了首项任务时，可在核验完成后继续该任务。

若创建只返回仍在准备中的 `clientThreadId`，只向用户展示已排队的新任务，保留旧任务不归档；不得把 `clientThreadId` 当作 `threadId` 调用读取、发送或归档工具。

## 验证后关闭旧任务

取得后继任务的 `threadId` 后，等待并回读其初始化结果。至少确认：项目身份正确、后继任务明确回报了唯一交接文档路径、适用规则和文档已完整读取、工作区状态能解释、易变化事实已经复核、待办和下一步与文档一致。

若初始化发现实质差异，先由后继任务在自己的当前工作区修正同一份交接文档并回读，或保持旧任务未归档并报告阻塞；不得用聊天中的第二份交接包掩盖差异。

全部通过后按顺序执行：

1. 将当前旧任务重命名为 `已交接｜<项目>｜<阶段>｜<YYYY-MM-DD>`。
2. 归档当前旧任务。
3. 在最终回复中展示后继任务入口，并简述旧任务的新标题和归档结果。

重命名失败时不归档。重命名成功但归档失败时，保留“已交接”标题并明确报告旧任务仍未归档。任何失败都不得创建第二个后继任务来重试。

唯一交接文档随项目长期保留。下次接力必须更新原文件，不新建按日期或任务命名的副本。

## 与个人记忆系统的关系

任务接力不依赖 Graphiti 或归档提取。旧任务归档后，可由既有计划任务按原规则处理其中的用户原话；本 Skill 不主动触发记忆扫描，也不把助手生成的交接包冒充用户事实。
