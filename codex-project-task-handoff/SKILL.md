# 普通项目任务接力

把用户口中的“换新会话”理解为新建一个普通 Codex 项目任务。用精简、可核验的交接包恢复项目上下文；不要复制旧任务的完整历史。

## 先判定接力对象

- 当前普通开发任务因为轮次多、上下文长，需要在同一项目继续查看、优化或下达新任务：使用本 Skill。
- 请求涉及 cc-connect、固定会话、移动端、飞书、微信、控制路由、`work_dir`、绑定代次或重新激活：停止本流程，改用 `cc-connect-collaboration`。
- “换会话”没有任何项目或路由线索且两者仍可能成立时，只问一个简短问题；未判明前不创建、改名或归档。

本 Skill 不读取或修改 cc-connect 的私有映射、路由账本、Bridge、ReplyCtx 或通道配置。

## 授权与不变量

- 只有用户在当前消息明确要求任务接力时才执行。不得仅因估算上下文长度、轮次、空闲时间或定时器自动触发。
- 一次明确的“创建后继任务并在成功后改名归档当前任务”授权覆盖这三个连续动作，但不授权提交、推送、部署、启停服务、删除文件或其他项目变更。
- 新任务未取得真实 `threadId`、未完成初始化或无法回读时，旧任务保持原名且不归档。
- 不删除旧任务，不改写其历史，不手工编辑 Codex 数据库、索引或会话文件。
- 不使用 `fork_thread`：它会复制已完成历史，无法达到缩短上下文的目的。
- 不使用 `handoff_thread`：它用于移动既有任务及 Git 状态，不用于创建精简上下文的后继任务。

## 生成交接包

读取 [交接包模板](references/handoff-package.md)，并只在当前项目范围内核验：

1. 项目名称、目录、目标和当前阶段。
2. 项目级与全局 `AGENTS.md`、唯一计划、README 和架构说明。
3. 当前 Git 分支、工作区改动、最近相关提交；不得重置、清理或擅自提交。
4. 已完成事项、验证证据、仍在运行的进程或后台任务。
5. 未完成事项、阻塞、已否决方案、风险边界和建议下一步。
6. 用户随接力请求明确下达的首项新任务；没有则写“仅初始化，等待用户下达任务”。

区分“当前回读确认”“旧任务中的历史结论”和“尚待验证”。不把敏感信息、完整终端输出、长对话、凭据或无关文件写入交接包。

## 创建并初始化后继任务

1. 先查询 Codex 已保存项目，优先复用当前任务的项目绑定；未绑定时，只在当前目录能唯一匹配一个保存项目时使用该项目。无法唯一定位则停止并请用户指定。
2. 创建普通项目任务，不创建 cc-connect 固定会话，标题使用 `<项目>｜<当前阶段或首项任务>`。
3. Git 项目默认使用独立 worktree。用户要求延续当前未提交状态或“从当前工作继续”时，从当前 working tree 创建；非 Git 项目使用保存项目的本地目录。除非用户明确指定，否则不覆盖模型和思考强度。
4. 初始提示必须包含交接包，并要求新任务先读取适用规则、项目计划和 Git 状态，核对差异后再继续。
5. 用户没有附带首项任务时，新任务只做只读初始化并回报准备状态，不修改文件或运行态；用户附带了首项任务时，可在核验完成后继续该任务。

若创建只返回仍在准备中的 `clientThreadId`，只向用户展示已排队的新任务，保留旧任务不归档；不得把 `clientThreadId` 当作 `threadId` 调用读取、发送或归档工具。

## 验证后关闭旧任务

取得后继任务的 `threadId` 后，等待并回读其初始化结果。至少确认：项目身份正确、适用规则已读取、工作区状态能解释、待办和下一步与交接包一致。

全部通过后按顺序执行：

1. 将当前旧任务重命名为 `已交接｜<项目>｜<阶段>｜<YYYY-MM-DD>`。
2. 归档当前旧任务。
3. 在最终回复中展示后继任务入口，并简述旧任务的新标题和归档结果。

重命名失败时不归档。重命名成功但归档失败时，保留“已交接”标题并明确报告旧任务仍未归档。任何失败都不得创建第二个后继任务来重试。

## 与个人记忆系统的关系

任务接力不依赖 Graphiti 或归档提取。旧任务归档后，可由既有计划任务按原规则处理其中的用户原话；本 Skill 不主动触发记忆扫描，也不把助手生成的交接包冒充用户事实。
