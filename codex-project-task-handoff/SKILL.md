# 普通项目任务接力

把用户口中的“换新会话”理解为新建一个普通 Codex 项目任务。每个项目只维护一个固定的项目内交接路径：Git 项目把该文件冻结到精确提交，非 Git 项目冻结同一目录中的路径和精确哈希，再让后继任务从冻结事实恢复上下文。不要复制旧任务的完整历史、依赖工作树未跟踪传播或为每次接力新增交接文件。

## 先判定接力对象

- 当前普通开发任务因为轮次多、上下文长，需要在同一项目继续查看、优化或下达新任务：使用本 Skill。
- 请求涉及 cc-connect、固定会话、移动端、飞书、微信、控制路由、`work_dir`、绑定代次或重新激活：停止本流程，改用 `cc-connect-collaboration`。
- “换会话”没有任何项目或路由线索且两者仍可能成立时，只问一个简短问题；未判明前不创建、改名或归档。

本 Skill 不读取或修改 cc-connect 的私有映射、路由账本、Bridge、ReplyCtx 或通道配置。

## 授权与不变量

- 只有用户在当前消息明确要求任务接力时才执行。不得仅因估算上下文长度、轮次、空闲时间或定时器自动触发。
- 用户当前明确要求执行项目任务接力时，视为同时授权为形成可交接基线而盘点、验证和修正明确归属的预期源码改动，维护唯一交接文档，创建逻辑提交，并在已有远端和明确分支均可验证时推送，再创建、初始化和关闭任务；项目规则更严格时从其规定。只读初始化、诊断或普通总结不触发这些动作。
- 接力授权不覆盖未知归属或预期外改动、敏感/运行态文件、创建或替换远端、强推、部署、启停服务、外部发送、真实交易或其他项目外动作；遇到这些边界报告 `HANDOFF_BLOCKED`。
- 唯一交接文档无法安全确定、无法写入、在 Git 项目中无法被跟踪，或无法被后继任务读取时，停止在创建后继任务之前并报告 `HANDOFF_BLOCKED`；不能退回只写聊天提示的旧方式。
- 新任务未取得真实 `threadId`、未完成初始化或无法回读时，源任务保持原名且不归档。
- 不删除源任务，不改写其历史，不手工编辑 Codex 数据库、索引或会话文件。
- 不使用 `fork_thread`：它会复制已完成历史，无法达到缩短上下文的目的。
- 不使用 `handoff_thread`：它用于移动既有任务及 Git 状态，不用于创建精简上下文的后继任务。

## 确定项目内唯一交接文档

先读取 [唯一交接文档与启动包模板](references/handoff-package.md)，再按以下顺序确定文件：

1. 读取适用的项目规则；如果规则已声明唯一交接文档，必须使用其精确路径。
2. 未声明时，默认使用项目根目录的 `PROJECT_HANDOFF.md`。若项目已有一份明确承担跨任务交接职责的文档，可继续沿用，但不得同时创建默认文件。Git 项目以仓库内唯一相对路径和提交历史为准；不同 worktree 只是该路径在不同检出中的实例，不得另起名称或形成并行事实源。
3. 在项目根目录及项目规则指定的文档目录中，按文件名和文件标题检查 `HANDOFF`、`SESSION_NOTES`、`CONTEXT`、`交接` 等用途相近的活动文档。发现两份及以上无法区分的活动交接文档时停止并报告 `HANDOFF_BLOCKED`，不擅自删除、覆盖或合并。
4. 时间戳副本、旧任务专属交接文件和新建的等价计划文件均不允许。历史归档若项目本来就有，只可只读保留，不能被当作当前交接入口。
5. 交接文档是“当前事实快照”，不是路线图、待办库或第二份项目计划；项目已有唯一计划时，只引用它，不复制或改写其职责。

Git 项目必须把交接文档纳入最终逻辑提交；不得只把它留在当前工作树或依赖未跟踪文件传播。非 Git 项目也在项目根目录或规则指定位置维护同一份文档。只有当前主协调任务更新该文档。

## 更新并核验交接文档

创建后继任务前，先以 UTF-8 原地更新唯一交接文档，并只在当前项目范围内重新核验：

1. 项目名称、目录、目标和当前阶段。
2. 项目级与全局 `AGENTS.md`、唯一计划、README 和架构说明。
3. 当前 Git 仓库根、分支或 ref、工作区改动、最近相关提交；不得重置或清理。逐项盘点状态，把路径分为“本次明确预期的源码/测试/文档/配置”“敏感或运行态排除”和“未知归属”。
4. 敏感或运行态包括 `.env`、凭据、Cookie、令牌、私钥、数据库、日志、缓存、虚拟环境、浏览器资料、下载/上传/输出/构建产物等，不得暂存或提交；不能只按目录名猜测，必须结合路径和项目规则判断。
5. 只验证和修正明确归属且预期的源码改动；未知归属、预期外删除、二进制或敏感风险直接报告 `HANDOFF_BLOCKED`，不批量 `git add`。
6. 对 Git 项目，把预期改动与唯一交接文档按职责做逻辑提交；提交前运行相应测试和 `git diff --cached --check`。交接文件必须被跟踪并进入最终提交。
7. 若存在既有远端，只推送既有远端和明确分支，不强推、不创建替代远端；推送后回读 upstream，确保没有未推送的本地提交或远端领先未整合提交。远端、分支或同步状态无法验证时报告 `HANDOFF_BLOCKED`。
8. Git 项目在最终提交后冻结 project、host、cwd、branch/ref、final HEAD、交接文件相对路径、精确 SHA-256、规范化辅助指纹和时间。非 Git 项目冻结保存项目、主机、同一项目目录、交接文件相对路径、精确 SHA-256 和时间，不伪造提交或 ref。项目外运行回执还记录源任务的完整 `threadId`、host 和原标题，供后继任务精确改名、归档；这些任务身份不得写入项目文件、仓库日志或最终用户回执。冻结后源任务不得再修改项目、交接文档、计划或相关运行态；发现漂移即阻断。最终 HEAD 和交接文件自身哈希只写入项目外的运行回执，不回写交接文档，避免自引用。
9. 已完成事项、验证证据、仍在运行的进程或后台任务。
10. 未完成事项、阻塞、已否决方案、风险边界和建议下一步。
11. 用户随接力请求明确下达的首项新任务；没有则写“仅初始化，等待用户下达任务”。

文档至少包含：更新时间与时区、项目身份、当前有效规则、已完成事项及证据等级、Git/工作区状态、服务和后台任务、未完成与阻塞、禁止动作、后继任务首项工作。区分“当前回读确认”“旧任务中的历史结论”和“尚待验证”，不得把计划写成已完成。

易变化事实必须在本轮重新读取；无法安全核验时写明“尚待验证”，不能沿用旧结论冒充当前状态。不把敏感信息、完整终端输出、长对话、内部会话标识、凭据或无关文件写入文档。复杂项目优先引用项目内事实源，避免让交接文档无限增长。

更新后必须回读并确认：

- 项目当前只有一个明确的活动交接入口；Git 项目中该文件还必须被仓库跟踪。
- 文档路径、更新时间、分支或版本、工作区改动、未完成事项和首项任务彼此一致。
- 没有新增等价计划、时间戳交接副本或敏感内容。
- Git 项目最终提交确实包含该文件；用 `scripts/validate_handoff_state.py` 回读分支、HEAD、精确文件 SHA-256、规范化辅助指纹和清洁工作区。该脚本只适用于 Git 项目；非 Git 项目直接回读固定路径和精确字节 SHA-256。
- 未知归属或任一门禁不满足时报告 `HANDOFF_BLOCKED`，不得为了通过核验而清理、覆盖或自动提交用户改动。

任一项不满足时不创建后继任务。

## 创建并初始化后继任务

1. 先查询 Codex 已保存项目，优先复用当前任务的项目绑定；未绑定时，只在当前目录能唯一匹配一个保存项目时使用该项目。无法唯一定位则停止并请用户指定。
2. 创建普通项目任务，不创建 cc-connect 固定会话。在尚未取得真实 `threadId` 前，初始标题使用 `<项目>｜<当前阶段或首项任务>｜H<令牌前8位>`；短令牌同时写入项目外冻结回执和启动提示，不能写入项目文件。
3. Git 项目只从精确、已提交且已验证的分支或 ref 创建独立 worktree；不得使用当前 `working-tree` 传播未跟踪文件。若当前 HEAD detached 或无法提供可用的已提交分支/ref，先报告 `HANDOFF_BLOCKED`，不猜分支、不创建临时分支。
4. 非 Git 项目使用同一保存项目的本地目录，以固定文件路径和精确 SHA-256 为门禁，不创建 worktree、提交或虚假 ref。
5. 初始提示只携带精简启动包：唯一交接文档相对路径、项目/主机定位、冻结时间、Git 项目的已提交分支或 ref 与精确 HEAD、文件 SHA-256、首项任务、短令牌、源任务完整 `threadId`/host/原标题和必要边界。源任务身份只用于最终精确改名与归档，不得写入项目文件、普通日志或最终用户回执。不要把整份交接文档、旧聊天、其他私有会话标识或敏感内容重复粘贴进提示。
6. 用户没有附带首项任务时，新任务只做只读初始化并回报准备状态，不修改文件或运行态；用户附带了首项任务时，也必须先通过后继只读门禁再继续。

若创建只返回仍在准备中的 `clientThreadId`，它只表示异步队列令牌，绝不能当作 `threadId` 调用读取、发送、改名或归档接口。按有界时间窗口查询既有任务，并用初始标题中的短令牌、保存项目和主机共同对账；零个或多个候选都报告 `HANDOFF_BLOCKED`。等待和对账期间不创建第二个后继任务。

## 验证后关闭旧任务

取得后继任务的真实 `threadId` 后，先把后继任务标题规范化为 `<项目>｜<当前阶段或首项任务>` 并回读，再等待并回读其初始化结果。Git 项目至少确认：实际 worktree 已注册；项目、主机、目录、分支或 ref、HEAD、唯一交接文档路径和精确文件 SHA-256 与冻结回执一致。非 Git 项目至少确认：保存项目、主机、实际目录、文件路径和精确 SHA-256 一致。两类项目都必须确认标题、适用规则、文档读取、工作区解释、易变化事实复核、待办和下一步，以及后继任务持有的源任务完整身份恰好匹配冻结回执；规范化指纹仅作辅助。

后继任务只读验证。若发现项目、目录、worktree 注册、分支、HEAD、文件路径、精确哈希、标题或运行态漂移，直接报告 `HANDOFF_BLOCKED`，不在后继任务修正文档、提交、推送或创建第二个任务。

源任务不自归档。全部门禁通过后，由后继任务按顺序：

1. 将源任务重命名为 `已交接｜<项目>｜<阶段>｜<YYYY-MM-DD>`。
2. 归档源任务。
3. 回读源任务标题和归档状态、后继任务入口及冻结回执。

重命名失败时不归档；重命名成功但归档失败时保留“已交接”标题并明确报告源任务仍未归档。任一步失败都不得创建第二个后继任务重试。

唯一交接文档随项目长期保留。下次接力必须更新原文件，不新建按日期或任务命名的副本。

## 离线状态验证器

使用 `scripts/validate_handoff_state.py` 只读验证 Git 仓库和交接文件。它支持 `--repo`、`--file`、`--expected-branch`、`--head`、`--sha256` 和 `--require-clean`；默认输出一行 JSON，成功退出 0，门禁失败退出 2。它会同时输出精确字节 SHA-256 与 CRLF/LF 规范化辅助指纹；只有精确哈希可以通过门禁。常见失败统一按 `HANDOFF_BLOCKED` 处置，包括 `NO_GIT`、`NO_HEAD`、`FILE_NOT_TRACKED`、`BRANCH_MISMATCH`、`HEAD_MISMATCH`、`FILE_SHA256_MISMATCH` 和 `DIRTY_WORKTREE`。非 Git 项目不运行该脚本，直接核验同一项目目录内的文件路径和精确哈希。

该脚本只检查事实，不能替代变更归属审查、测试、逻辑提交、远端推送、真实 worktree 注册或后继任务回读。

## 与个人记忆系统的关系

任务接力不依赖 Graphiti 或归档提取。旧任务归档后，可由既有计划任务按原规则处理其中的用户原话；本 Skill 不主动触发记忆扫描，也不把助手生成的交接包冒充用户事实。
